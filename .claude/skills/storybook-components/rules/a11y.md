# Accessibility — the posture, and what axe cannot see

**The baseline is already at ceiling. Protect it; do not propose work here.**
`.storybook/preview.tsx` sets `a11y: { test: "error" }` project-wide. Across the whole story tree there
are zero per-story or per-meta `todo`/`off` overrides and zero disabled rules. The one global exclusion
(`[data-base-ui-focus-guard]`) cites the upstream Base UI issue in a comment. A story that suppresses
the check fails the build — `hephaestus/no-story-a11y-override` reads both `parameters.a11y` and
`globals.a11y`; if a rule genuinely misfires, the exclusion goes in `preview.tsx` with the upstream
link beside it.

**A green axe panel is the floor, not the goal.** The addon *"automatically catches up to 57% of WCAG
issues"*. Everything below is what it misses.

## The three things axe does not check for us

1. **A name that disambiguates two instances on one screen.** Axe sees "has an accessible name"; it
   cannot see that both copies are called the same thing. A component with no visible label *requires*
   `aria-label`/`aria-labelledby` in its props type — see `props-state-shape.md` rule 5.

2. **A state conveyed by colour needs a second channel.** The registries make `icon` required for
   exactly this reason — see `vocabulary-registries.md` rule 1 (WCAG 2.2 SC 1.4.1).

3. **`aria-invalid` announces *that* a field is wrong and never *why*.** A field marked `aria-invalid`
   also points `aria-describedby` at the element carrying its message, so a reader tabbing back to it
   hears the reason rather than "invalid" alone (WCAG 2.2 SC 3.3.1). Use `aria-describedby`, **not** a
   live region — a live region re-announces on every keystroke.

## Hover cards carry supplementary content only

A hover card must never hold the only copy of a fact, or the only control that reaches one: hover is
unavailable on touch and awkward on keyboard. Everything in the card must also be on the page its link
goes to.

The normative rule is WCAG 2.2 SC 1.4.13 — content shown on hover or focus must be **dismissible**
(*"A mechanism is available to dismiss the additional content without moving pointer hover or keyboard
focus, unless the additional content communicates an input error or does not obscure or replace other
content"*), **hoverable** (*"the pointer can be moved over the additional content without the additional
content disappearing"*) and **persistent** (*"remains visible until the hover or focus trigger is
removed, the user dismisses it, or its information is no longer valid"*). The "destination is a superset
of the card" clause on top of that is house policy.
<https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html>

## Hide rather than disable, for permissions specifically

Disabling is the better default for a control the user could still unlock. For a control their role
will never unlock, hide it — and note that a native `disabled` button is unreachable by keyboard, so a
tooltip explaining why can never be read. Details in `webapp/AGENTS.md` § Role-based gating.

## The A+ move

Assert the invariant axe is blind to: that a disabled control is genuinely out of the tab order
(`expectGenuinelyDisabled`, `src/test/controls.ts`), or that an error field's `aria-describedby` points
at the element carrying the message. A regression then fails the suite instead of silently degrading.
