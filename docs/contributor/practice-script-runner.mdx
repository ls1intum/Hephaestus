# Practice script runner

This page describes how the review runner runs the program of each admitted practice.
The host is `pi-runner.ts` in the review container.
Its library is `docker/agents/practice-scripts/lib/`, and `lib/program-host.ts` runs one program.

### One program for each practice

Every admitted practice runs exactly one program, and the program returns one candidate result.
A practice whose revision holds a script runs that script as a custom program.
A practice without a script runs the built-in program, `BUILTIN_PROGRAM` in `lib/program-host.ts`:

```ts
export const BUILTIN_PROGRAM = definePracticeScript({ meta: {}, run: async (ctx) => ctx.review() });
```

The built-in program runs in the host process.
A custom program runs in its own child process, through `child.ts`.
Both get the same context from `lib/program-context.ts`.
The host checks the value that each returns in the same way.

### Retired forms

The child checks that the default export is a `definePracticeScript` definition.
If it is not, the practice fails with the stop reason `invalid-program` and the error `RETIRED_FORM_ERROR` from `lib/contract.ts`.
A script whose `meta` has `version`, `kinds` or `tokens` fails with `invalid-program`.
Its error is `LEGACY_CONTRACT_ERROR`, and the error names the retired key.
A `run` that returns leads fails with the stop reason `invalid-candidate` and the same error.

Such a practice has no result in this review.
Its error never becomes a statement about the work.
The [practice catalogue](./practice-catalogue.md#practice-scripts) tells how the server upgrades a bundled script that nobody changed.

`lib/practice-script.ts` is the only import that the admin page documents.
It re-exports the readers that a workspace script needs.
A bundled script can also import other modules of `lib/` directly.
A workspace that customized a bundled practice keeps a copy of its script, so such an import must stay valid.

## Writing a bundled script

A bundled script is `server/application/src/main/resources/practices/scripts/<slug>.ts`.
The [practice catalogue](./practice-catalogue.md#practice-scripts) tells how a bundled practice and its script change.

1. Write the script with `definePracticeScript`, as [Write a practice script](/admin/practice-scripts) tells.
2. Import from `docker/agents/practice-scripts/lib/practice-script.ts` where it exports what you need.
3. Put shared readers and scanning mechanics in `docker/agents/practice-scripts/lib/`.
4. Put the predicates of one practice in its script.
5. Add the tests that [Testing](#testing) describes.

## How the host runs the programs

The host runs the programs in this order:

1. The host decides if the attempt continues an admitted review. A continuation runs no program, derives no change and admits nothing.
2. Otherwise, the host derives the change view `work/change/` with `pi-change.ts`.
3. The host runs one practice at a time, in the order of its turns. A turn holds the practices of one catalog group.
4. For each practice, the host reads and validates the staged inputs. If they are not valid, the practice fails with the stop reason `unavailable`.
5. The host runs the program of the practice until it returns, fails, or reaches its deadline.
6. The host checks the returned value as one candidate.
7. When the measuring window ends, the host admits all candidates in one call.

### A custom program

A custom program runs in these steps:

1. The host starts `child.ts` with the [process grants and limits](./agent/workspace-abi.mdx#practice-script-validation-and-limits).
2. The host sends the job: the slug, the inputs, the criteria, the pinned files, the time and the deadline.
3. The child imports the program, checks its default export, and sends `meta` to the host.
4. The host validates `meta` with `parseMeta` in `lib/contract.ts`.
5. If a `required` slot has no model, the host stops the child with the status `skipped`.
6. Otherwise, the host replies with the available slots and the tokens left in the attempt's direct-model account.
7. The child builds the context, calls `run`, and sends one final message: the value or the failure.

A slot is available when `practice-script-models.json` has a model for it and the protocol of that model serves the slot.
`lib/contract.ts` holds the slots, the protocols, the reasons, the stop reasons and the entry limits of one call.
`PracticeScriptContractSyncTest` keeps these names equal to the Java side.
`PracticeScriptCapsSyncTest` keeps `MODEL_SLOT_CAPS` equal to the entry limits of `LlmProxyService`.

### The messages between the host and a child

`lib/ipc.ts` defines the messages.
The host sends a `HostMessage`: `job`, `meta-accepted`, `model`, `model-failed`, `read-result`, `read-failed`, `review-result`, `review-failed` and `abort`.
The child sends a `ChildMessage`: `meta`, `model`, `read`, `review`, `cancel`, `log`, `result` and `failed`.
The host trusts its own messages.
It parses each child message with `childMessageSchema`, because the child runs code that a workspace admin wrote.

These rules apply in `lib/script-run.ts`:

- Each `model`, `read` and `review` request carries a call ID. The host answers each ID once.
- A message that does not parse stops the program.
- A message larger than `MAX_IPC_MESSAGE_BYTES` stops the program.
- More requests in flight than `MAX_IN_FLIGHT` stop the program.
- A request that uses the ID of an open request stops the program.
- A `model` or `review` request before `meta` fails the program with `invalid-program`.
- A child sends exactly one final message, `result` or `failed`. A second final message fails the program.
- After `abort`, the host answers no request and sends no late reply.
- No message carries provenance. The server computes the provenance of a result at admission.

[Process grants and limits](./agent/workspace-abi.mdx#practice-script-validation-and-limits) owns the IPC bounds.

### Reads through the host

A program reads the reviewed work through `ctx.files` and `ctx.evidence`.
The host answers each read with `EvidenceReader` in `lib/evidence-reader.ts`.
It reads from the pinned checkout, the change view and the captured records.
Each read leaves a receipt: read, cut short, or failed.
A missing file is `ABSENT`, but a read that fails throws the reason `unavailable`.
The `.git` folder of the repository reads as absent.

A search through `grep` also runs in the host, because the child cannot start a program.
The built-in program uses the same reader in the host process.

### What a program reads about its review

The server stages these inputs, and the host validates them once, before the program starts:

1. For each admitted practice, `PracticeScriptInputs` writes `<slug>.cause.json` and `<slug>.previous.json` to `work/practice-scripts/practices/`.
2. For a practice with a script, `PracticeCatalogInjector` writes `<slug>.ts` beside them.
3. `PracticeRunnerProfile.setupCommands()` links `work/practice-scripts/lib` to `/opt/practice-scripts/lib` before Node starts.
4. `InputReader` in `lib/script-inputs.ts` reads the two files and the record of the work.
5. `InputReader` validates the three with `practiceInputsSchema` in `lib/contract.ts`.

Only the worker prepares a review, so only the worker writes the inputs.
`PracticeScriptInputs` is not a bean of its own.
The link lets a staged program import `../lib/…`, and lets the host import `./work/practice-scripts/lib/…`.

The record is `metadata.json` for a pull request or an issue.
It is `conversation_thread.json` for a conversation, and `document.json` for a document.
An error names the file that holds it.
A missing or invalid input fails the practice with the stop reason `unavailable`, and no program starts.

The record schemas follow what the content sources write.
A field that is wrong for an identity, a role, a revision or a structure fails the record.
Only a descriptive field with a defined meaning for "not known" falls back to it.
Such a field reads a value that the schema does not name, such as a new pipeline state, as not known.
`notKnownWhenUnnamed` in `lib/contract.ts` marks these fields: `head_checks` and `sub_issues_source`.
An issue's `state` reads such a value as `UNKNOWN`.

The cause file holds `kind`, `subject.role`, `practice.revisionId`, `scope` and `cause`.
`scope.key` is `<kind>:<artifactId>:<ROLE>`, and a reviewer's pass over one submitted review adds `:review:<reviewId>`.
A program treats the key as opaque, and admission stores it on the result.

The practice's moments and review conditions are its review occasion.
The cause tells which of them brought the practice into this review, or that a recheck or a request by hand did.
The server derives `cause.type` from the job:

| `type` | When |
| --- | --- |
| `requested` | The job's trigger mode is `MANUAL`: a request by hand or a campaign over earlier work. Such a job has no `signal` in the file. |
| `recheck` | The slug is in the job's `rechecked_practices`, and the practice is not bound to the job's signal under its `review_state`. |
| `moment` | Every other practice. On `scm.pull_request.reviewed`, the file also has `review`: the job's `review_id` and the login of its `about_user_id`. |

`origin` is the job's `observation_origin`, `state` its `review_state`, and `admittedAt` its creation time.

The previous file holds `null`, or the current result of the practice about the review's person on the same work.
The server reads it as the review reads history.
It applies `LatestRun.perClaim` over `PracticeResultRepository.findStandingForWork`, then `ResultVisibilityPolicy.permitsAll`, then the consent of a conversation's channel.
Thus, the server does not stage a result that an admin invalidated, a stale result, or a result whose evidence is no longer authorized.
An older result does not take their place.

The file holds `practiceResultId`, the outcome, the severity and the citations.
It holds no summary, no explanation and no delivery state.
For a pull request, it holds the `head` of the earlier run's `reviewedWork`.

`KINDS`, `MOMENTS` and `REVIEW_STATES` in `lib/contract.ts` repeat the artifact descriptors, which stay their home.
`PracticeScriptContractSyncTest` keeps them equal, with the origins, outcomes, severities, subject roles and file suffixes.

#### The change since the previous review

When `previous.head` is set, the host asks git if it is an ancestor of the reviewed head, `work.commit_sha`.
If it is, the program gets `previous.changeSince`: the parsed diff from `previous.head` to the reviewed head.
If it is not, as after a force push, `changeSince` is absent, and the host logs why.
An empty `changeSince` means that the work did not change.
The host computes each change once and shares it between the practices with the same `head`.

When the host resolves the leads of a review input, it marks each lead on a new-side line that `changeSince` adds.
The section of that review marks each such lead with `(new)` and counts them.
The execution report does not carry the count.

### A review of one practice

`ctx.review(options)` asks the host for one review of the program's practice.
The host runs at most one practice and at most one review at a time.
A concurrent or nested call to `review()` rejects with the reason `refused`.
The host checks the options with `parseReviewOptions`.
Invalid options reject the call with `error` before a review starts.

The host prepares the review input in these steps:

1. The host resolves each lead to the line that its source holds, with `lib/leads.ts`.
2. A lead that its source does not hold is an error of the program, never dropped.
3. The host renders a section from the leads, facts, directions, context and limitations.
   [Review input](/admin/practice-scripts#review-input) owns its bound.
4. The host writes the whole input to `work/review-input/<slug>.json`, for the session to read past the section.

The host then opens a fresh native session for this call.
The session receives the task, the brief, the practice's criteria, the result illustrations and the section.
Its tools are the evidence tools, `bash`, `codemode` and `submit_result`.

`submit_result` fills a draft that is private to this call.
The host first normalizes the submission with `pi-result-normalize.ts`.
It checks the sources, the scope and the quotes, and then `parseCandidate` with host coverage.
The host measures that coverage from the read receipts of the session.
When the session ends, `review()` returns the draft.
Without a draft, it rejects with the reason that the session gave no result.

The host removes `work/review-input/` before admission.
A native session that does not stop ends the run, and no later session starts.

### The final candidate

The program returns the final candidate.
It can return the candidate of its review, change its words, or return a candidate of its own.
`runPracticeProgram` checks the value with `parseCandidate` in `lib/contract.ts`.

- A value that is not a candidate fails the practice with `invalid-candidate`.
- A candidate with `coverage.source: "host"` must carry coverage that a review of that practice returned, unchanged.
- Other host coverage fails the practice with `invalid-candidate`.
- A program that throws an `UnratedError` fails with its reason.

### Admission

The host sends all final candidates in one `POST {LLM_PROXY_URL}/admit-results`:

```json
{ "schemaVersion": 2, "results": [ { "practiceSlug": "…", "candidate": { } } ] }
```

The results are sorted by slug, with one entry for each slug.
The body names no job and no attempt, because the identity comes from the token only.
The server answers with the admitted results, the withheld practices and the admission digest.
Composition starts after that answer.
`result.json` and `review-state.json` in `out/` hold the request body.
The [practice review pipeline](./practice-review-pipeline.mdx) owns the admission rules.

A continuation runs no program, derives no change and admits nothing.
Its `result.json` in `out/` is `{ "schemaVersion": 2, "results": [] }`, and it writes no execution report.

## Budget

An attempt has one budget for time and one account for direct model calls.

### Time

The host receives its work deadline as `AGENT_BUDGET_MS`.
[Workspace ABI](./agent/workspace-abi.mdx#practice-script-validation-and-limits) owns the shutdown reserve and program deadlines.
When composition was requested, the measuring window keeps 85% of that budget, and composition keeps the rest.

### Direct model calls

The direct model calls of all practices share one attempt account, `ModelBudget` in `lib/models-host.ts`.
The host takes its size from `PI_DIRECT_MODEL_TOKENS`.
The server sets that variable from `hephaestus.practice-review.direct-model-tokens-per-attempt`.
[Cost and limits](/admin/ai-providers#cost-and-limits) owns the environment variable and default of that setting.
A later practice sees only what the earlier practices left.

The host reserves tokens before each call, and the reservation is an estimate.
When the call ends, the host settles the account with the tokens that the provider reported.
A call that fails, is cancelled, or reports no tokens keeps its reservation, because the provider can have billed it.
A call that the account cannot hold does not run, and its reason is `budget`.

The LLM proxy enforces the same token cap again for the attempt.
It also counts the search units of reranking calls against `direct-model-search-units-per-attempt`.
Past either cap, the proxy refuses further direct calls.
[Cost and limits](/admin/ai-providers#cost-and-limits) gives the purses that the proxy also enforces.

`MODEL_CONCURRENCY` in `lib/concurrency.ts` enforces the [direct-call limit](/admin/practice-scripts#limits) for all practices together.

### Review sessions

The calls of a review session do not spend the direct-model account.
All review sessions in a catalog-group turn share its [work budget](/admin/practice-review-operations#work-budgets).
A new `ctx.review()` call does not reset that budget.

### Cancellation

The host stops a program for one of three reasons: `deadline`, `budget` or `cancelled`.
When it stops a custom program, it sends `abort` to the child.
Each open request fails at once with that reason, and the host cancels the call behind it.
If the child has not ended `RETURN_MS` later, the host kills it.
The host sends no reply that arrives after the abort.

The end of the measuring window aborts every program that still runs.
A practice that the host did not start has the status `not-reached`.
Its stop reason is the reason that the run stopped.

## Model calls through IPC

`ctx.models` in the child are stub objects from `lib/models-ipc.ts`.
Each call goes to the host as a message.
`hostModels` in `lib/models-host.ts` makes the call against the LLM proxy with `LLM_PROXY_TOKEN`, the one job token.
The child never holds a token.

A decision model with the `openai-decisions` protocol calls the [OpenAI Decisions API](https://developers.openai.com/api/docs/guides/decisions).
On an `openai-completions` model, the host asks for one letter for each question and reads `top_logprobs` at each answer position.
This adapter works only with models that return log probabilities, such as vLLM deployments and OpenAI chat models without reasoning.

The host refuses a call that holds more entries than the entry limit of its slot, `MODEL_SLOT_CAPS` in `lib/contract.ts`.
Its reason is `too-large`.
The embedding stub sets `maxEmbeddingsPerCall` to its limit, so the AI SDK splits a larger `embedMany` into calls within the limit.
`classify` packs its questions with `PACK_SIZE` in `lib/practice-script.ts`, which stays below the decision limit.
It keeps at most `MODEL_CONCURRENCY` packs in flight, through `eachBounded` in `lib/concurrency.ts`.

On the Decisions, Embeddings and Rerank APIs, the proxy enforces the same limits with HTTP 413.
A decision call to a Chat Completions model has only the host's check.

## What the host records

The host writes the execution report `practice-scripts.json` into `out/` when the run ends.
It has one entry for each admitted practice, the built-in programs and the practices not reached included.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-report) gives its shape.

An entry gives the program kind and digest, the status, the stop reason and the calls.
It also gives the reads that the program and its reviews reached, and the run time.
The digest is the SHA-256 of the staged bytes of a custom program, and `null` for the built-in program.
The status `ok` means that a candidate passed the host's checks.
Admission is a separate step, and admission can still withhold that candidate.
The report holds no candidate and no tokens, because the proxy counts the tokens.

The server stores the status as `PracticeScriptRunStatus`: `OK`, `SKIPPED`, `FAILED`, `NOT_REACHED` or `NOT_FINISHED`.
`NOT_FINISHED` is the status of an admitted practice that a complete report does not name.
The server derives `PracticeProgramPath` from the calls: `CODE`, `MODELS`, `REVIEW` or `MIXED`.
At admission, the server computes the provenance of each result from its own pinned data, the program digest included.

## What a script can reach

A practice script is code that a workspace admin writes.
Hephaestus trusts it like the practice definition that it belongs to.
The script still never holds a credential.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-validation-and-limits) gives the grants of the program's process.

The [Node permission model](https://nodejs.org/docs/latest-v24.x/api/permissions.html) is a seat belt, not a sandbox.
It follows symbolic links, and it does not restrict the network.
Thus, a token must not be in a process that runs script code:

| Process | Token in its environment |
| --- | --- |
| The container's PID 1 and the review host, `pi-runner.ts` | `LLM_PROXY_TOKEN`, the one job token of the attempt |
| The process of a custom program | None. Its environment is empty. |

The direct-model route `/internal/llm/practice-script/{slot}/**` takes the same job token as the review session.
The proxy refuses a mentor credential on that route with HTTP 403, because the route bills a review attempt.

A program's process may read only the toolkit install, its dependency folders and the stage, `work/practice-scripts/`.
It can read the `/proc/<pid>/environ` of another process only through a symbolic link in such a folder.
No untrusted party can put such a link there:

- The server stages the inputs only as regular files.
- The program's process has no write grant.
- The only link in the stage is the fixed `lib` link.

The model calls and reads of a program have these controls:

| Control | Effect |
| --- | --- |
| Model calls through IPC | Each call goes to the host as a message, and the host makes it with a credential that the program never holds. |
| Reads through the host | The program reads the work only through the host, which reads only the pinned captures and keeps a receipt of each read. |
| Request allowlist | The host keeps only the fields that a direct model call can set. It drops provider options and headers. Chat keeps only function tools. |
| Practice header | The host names the program's practice on each call. A program cannot name another practice, because the allowlist drops its headers. |
| No default provider | `lib/models-ipc.ts` sets the AI SDK [global provider](https://ai-sdk.dev/docs/ai-sdk-core/provider-management#global-provider-configuration) to an empty provider, so a program cannot reach another provider through it. |
| Parsed messages | The host parses every message with zod. A message that does not parse stops the program. |

The [workspace ABI](./agent/workspace-abi.mdx#models-for-practice-scripts) gives the practice header.

## How the server learns needs

A script declares `meta.models` in code, and the server does not parse scripts.
Thus, the server knows what a script needs only after a review runs it.

The server stores the execution report of each review attempt as `agent_job_practice_script_run` rows, one for each admitted practice.
A row holds the status, the program kind and digest, the stop reason, the calls and the reads reached.
It also holds the declared models, the run time, and the error line of a failed program.
A program that the host did not reach has no models in its row.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-report) describes the report.

The job's snapshot holds only the models of its latest attempt.
Thus, a row of an earlier attempt cannot read its tiers from the snapshot.
The row itself stores the tier of the model that the attempt froze for each declared model.
A retry cannot change the tiers of an earlier attempt.
The proxy records the calls and tokens of each slot in an `agent_job_practice_script_usage` row, with the tier of the model that served them.
Thus, a program that did not finish still shows the tier of each model that it called.

`GET /workspaces/{workspaceSlug}/agents/jobs/{jobId}/practice-scripts` returns the rows of the current attempt of one review.
It joins them with the usage rows of that attempt.
Only the attempt's terminal write records its rows.
Thus, the list is empty while a retry runs, and a retry never shows the rows of an earlier attempt.

`GET /workspaces/{workspaceSlug}/practices/practice-script-needs` serves the needs to workspace admins.
It gives one entry for each practice with a script.
The entry has the needs from the newest run that reported the script's models.
For each need, it names the tiers that no ready assignment serves now.
When that run ran an earlier version of the script, the entry gives `scriptChanged: true` and no needs.

`MemberAiRoutingAdapter.practiceScriptBinding` chooses the model of each slot of a practice script for one developer.
Its ceiling is the stricter of the developer's AI choice and the tier of the review's own model for that developer.
The job's slots and the claim check call it, through `ReviewMemberAiPolicy`.
The needs endpoint calls `unservedTiers` through `PracticeNeedsAdapter`.
`unservedTiers` applies the same ceiling to each member tier, through `serving`.

The LLM proxy does not apply this rule again.
Before each call, it checks only that the model fits the developer's own AI choice.
[Privacy](/admin/ai-providers#privacy) states the rule for admins.

`server/application/src/test/resources/practice-results/` holds the shared fixtures.
They are candidates, an admission request and reply, an execution report, and invalid candidates with their refusal codes.
Both languages read them.
Do not change a fixture for one side only.

Run one TypeScript file with `node --test <file>`.
`vp run test:agents` runs all of them.
The Java tests run in the server's test tiers (`server/AGENTS.md` § Test tiers).

`test/proxy-stand-in.ts` serves the direct model routes, `POST /practice-script/<slot>/<operation>`.
It checks the bearer token and records each request.
A test gives it a handler that answers by item.
A handler must throw for an item that it does not know, so that a changed prompt fails the test.
A test asserts what the host guarantees, never the wording of a real model.

To test a new script:

1. Put a fixture next to the others in `docker/agents/practice-scripts/fixtures/`.
2. Add a case to `definition.test.ts` that runs the fixture with no models.
3. Assert the review input that the program asks for, or the candidate that it returns.
4. Add a case for each slot with a stand-in handler that answers by item.
5. Assert the `models` and `calls` of the outcome.

`validate.ts` runs one program on a repository without models and without a review session.
[Run a program on your own change](/admin/practice-scripts#run-a-program-on-your-own-change) gives its options.
`live.test.ts` shows how to run a program with models behind the stand-in.
`fixtures/every-slot.ts` uses every primitive and every slot.
