# Practice script runner

This page describes how the practice script runner runs a practice's script.
The runner is `docker/agents/practice-scripts/runner.ts`, and its library is `docker/agents/practice-scripts/lib/`.

### Two contracts

The runner runs two contracts.
The child process tells them apart by the shape of the default export.

| Contract | Default export | Returns | Can call models | Deadline |
| --- | --- | --- | --- | --- |
| **Positional** | `(repo, diffFiles, metadata, contextDir, changeDir, contextReference) => result` | Hints, metrics and directions | No | The positional deadline |
| **Definition** | `definePracticeScript({ meta, run })` | Leads, facts, unrated items and directions | Yes | The definition deadline, which is longer, because the script can wait for models |

The positional contract is the supported legacy contract of the bundled scripts.
Every bundled script uses it, so the runner must keep it while a bundled script or a customized copy of one uses it.
The [practice catalogue](./practice-catalogue.md#practice-scripts) describes it.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-validation-and-limits) gives both deadlines.

`lib/practice-script.ts` is the only import that the admin page documents.
It re-exports the readers that a workspace script needs.
A bundled script can also import other modules of `lib/` directly.
A workspace that customized a bundled practice keeps a copy of its script, so such an import must stay valid.

## Writing a bundled script

A bundled script is `server/application/src/main/resources/practices/scripts/<slug>.ts`.
The [practice catalogue](./practice-catalogue.md#practice-scripts) tells how a bundled practice and its script change.

1. Write a new bundled script with the definition contract, as [Write a practice script](/admin/practice-scripts) tells.
2. Import from `docker/agents/practice-scripts/lib/practice-script.ts` where it exports what you need.
3. Put shared readers and scanning mechanics in `docker/agents/practice-scripts/lib/`, and the predicates of one practice in its script.
4. Add the tests that [Testing](#testing) describes.

## How the runner runs a script

The runner starts one Node process for each script, through `child.ts`.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-validation-and-limits) gives how many run at a time, their grants, and their deadlines.

A definition script runs in these steps:

1. Before the child starts, the runner reads and validates the script's inputs.
   [What a script reads about its review](#what-a-script-reads-about-its-review) tells how.
2. The child imports the script and sends `meta` to the runner.
3. The runner validates `meta` with the zod schema in `lib/contract.ts`.
4. If the inputs of step 1 are not valid, the runner stops the child with the status `error`.
5. The runner decides which declared slots are available.
6. If a `required` slot is not available, the runner stops the child.
7. Otherwise, the runner replies with the available slots and the token limit of the practice.
8. The child builds the context from the inputs, calls `run`, and sends the result.
9. The runner validates the result with zod and settles the leads.
   It marks the new leads, and writes the section and the result.

[Write a practice script](/admin/practice-scripts#meta) gives the status of a script that step 3, 4 or 6 stops.
A positional script does not read the inputs, so step 4 does not stop it.

A slot is available when `practice-script-models.json` has a model for it and that model's protocol serves the slot.
`lib/contract.ts` holds the slots, the protocols, the reasons, the entry limits of one call, and the run statuses.
`PracticeScriptContractSyncTest` keeps the slots, protocols, reasons and statuses equal to the Java side.
`PracticeScriptCapsSyncTest` keeps `MODEL_SLOT_CAPS` equal to the entry limits of `LlmProxyService`.

### What a script reads about its review

The context of a definition script has a `kind`, a `work`, a `cause` and a `previous`.
[The context](/admin/practice-scripts#the-context) gives their fields.
The server stages them, and the runner validates them once, before the script starts:

1. For each practice with a script, `PracticeCatalogInjector` writes `<slug>.ts` to `work/practice-scripts/practices/`.
   Beside it, `PracticeScriptInputs` writes `<slug>.cause.json` and `<slug>.previous.json`.
   Only the worker prepares a review, so only the worker writes them.
   `PracticeScriptInputs` is no bean of its own.
2. `pi-practice-scripts.ts` copies the three files of each practice to the stage.
3. The runner reads the two files beside the script.
   It reads the record of the work from the context folder.
   The record is `metadata.json` for a pull request or an issue.
   It is `conversation_thread.json` for a conversation, and `document.json` for a document.
4. The runner validates the three with `practiceInputsSchema` in `lib/contract.ts`.
   An error names the file that holds it.
   An error fails the practice with the status `error`, as the other errors of a script do.

The cause file holds `kind`, `subject.role` and `cause`.
The practice's moments and review conditions are its review occasion.
The cause tells which of them brought the practice into this review, or that a recheck or a request by hand did.
The server derives `cause.type` from the job:

| `type` | When |
| --- | --- |
| `requested` | The job's trigger mode is `MANUAL`: a request by hand or a campaign over earlier work. Such a job has no `signal` in the file. |
| `recheck` | The slug is in the job's `rechecked_practices`, and the practice is not bound to the job's signal under its `review_state`. |
| `moment` | Every other practice. On `scm.pull_request.reviewed`, the file also has `review`: the job's `review_id` and the login of its `about_user_id`. |

`origin` is the job's `observation_origin`, `state` its `review_state`, and `admittedAt` its creation time.

The previous file holds `null`, or the current claim of the practice about the review's person on the same work.
The server reads it as the review reads history:
`LatestRun.perClaim` over `ObservationRepository.findStandingForWork`, then `ObservationVisibilityPolicy.permitsAll`, then the consent of a conversation's channel.
Thus, the server does not stage a claim that an admin invalidated, a stale claim, or a claim whose evidence is no longer authorized.
An older claim does not take their place.

The file holds the outcome, the severity and the citations.
It holds no summary, no rationale and no delivery state.
For a pull request, it holds the `head` of the earlier run's `reviewedWork`.

`KINDS`, `MOMENTS` and `REVIEW_STATES` in `lib/contract.ts` repeat the artifact descriptors, which stay their home.
`PracticeScriptContractSyncTest` keeps them equal, with the origins, outcomes, severities, subject roles and file suffixes.

#### The change since the previous review

When `previous.head` is set, the runner asks git if it is an ancestor of the reviewed head, `work.commit_sha`.
If it is, the runner gives the script `previous.changeSince`: the parsed diff from `previous.head` to the reviewed head.
If it is not, as after a force push, `changeSince` is absent, and the runner logs why.
An empty `changeSince` means that the work did not change.
The runner starts git, because a script's process has no child-process grant.
It computes each change once and shares it between the practices with the same `head`.

After the runner settles the leads, it marks each lead that cites a new-side line of the change that `changeSince` adds.
The result counts them in `newSinceLastReview`.
The section says how many leads are new, and marks each with `(new)`.
The practice script report to the server does not carry the count.

### Model calls through IPC

`ctx.models` in the child are stub objects from `lib/models-ipc.ts`.
Each call goes to the runner as a message.
`lib/models-host.ts` in the runner makes the call against the LLM proxy with `PRACTICE_SCRIPT_PROXY_TOKEN`, which the child never holds.
`ctx.tools.grep` also runs in the runner, because the child cannot start a program.

A decision model with the `openai-decisions` protocol calls the [OpenAI Decisions API](https://developers.openai.com/api/docs/guides/decisions).
On an `openai-completions` model, the runner asks for one letter for each question and reads `top_logprobs` at each answer position.
This adapter works only with models that return log probabilities, such as vLLM deployments and OpenAI chat models without reasoning.

The runner refuses a call that holds more entries than the entry limit of its slot, `MODEL_SLOT_CAPS` in `lib/contract.ts`, with the reason `too-large`.
[Limits](/admin/practice-scripts#limits) gives the values.
The embedding stub sets `maxEmbeddingsPerCall` to its limit, so the AI SDK splits a larger `embedMany` into calls within the limit.
`classify` packs its questions with `PACK_SIZE` in `lib/practice-script.ts`, which stays below the decision limit.
On the Decisions, Embeddings and Rerank APIs, the proxy enforces the same limits with HTTP 413.
A decision call to a Chat Completions model has only the runner's check.

### Token accounting

The runner reserves tokens before each call, against the token limit of the practice and the attempt token limit.
[Limits](/admin/practice-scripts#limits) gives the size of a reservation.
When the call ends, the runner settles the account with the tokens that the provider reported.
A call that fails, is cancelled, or reports no tokens keeps its reservation, because the provider can have billed it.
The LLM proxy enforces the attempt token limit and the purses again, as [Cost and limits](/admin/ai-providers#cost-and-limits) tells.

`MODEL_CONCURRENCY` in `runner.ts` limits the model calls in flight for all scripts together.
`MAX_IN_FLIGHT` in `lib/script-run.ts` stops a script that has too many requests in flight.
[Limits](/admin/practice-scripts#limits) gives both values.

## What the runner records

When a practice ends, the runner writes `<slug>.md`, the section, and `<slug>.json`, the result.
A definition script's result has these fields:

| Field | Meaning |
| --- | --- |
| `contract` | `definition`. |
| `status` | `ok`, `skipped`, `error`, or `timeout`. `timeout` means that the runner stopped the script at its deadline, or that the stage ended before the script started. |
| `durationMs` | The time from the start of the script to its result. |
| `leads`, `facts`, `unrated`, `directions`, `kinds` | What the script returned, after the runner settled the leads. Each lead carries the quote that the runner wrote and its rating score. A lead on a line added since the previous review has `newSinceLastReview: true`. |
| `newSinceLastReview` | How many leads cite a line added since the previous review. Absent when the change since that review is not known. |
| `dropped` | The leads that the runner did not show. |
| `models` | Slot → `{ need, bound, notRated }`. `bound` tells if the job has a model for the slot. `notRated` counts the calls that the runner could not rate, by reason. |
| `error` | For `error` and `timeout`, why the script failed or was stopped. The report `practice-scripts.json` keeps its first line for `error` only, as the [workspace ABI](./agent/workspace-abi.mdx#practice-script-report) tells. |

A positional script's result has `contract` (`positional`), `status` (`ok`), `durationMs`, `hints`, `dropped`, `metrics` and `directions`.
There, `dropped` counts the changed-line hints that the runner did not show.

A script that fails before it sends `meta`, or that never starts, gets a result of the same shape with the contract `unknown`.
Its status is `error` or `timeout`.
Only a valid result without `meta` shows that a script is positional.
Thus, a positional script that fails is also `unknown`.
Its needs are not known, so the server records no models for it.

The result holds no tokens and no calls.
The proxy counts those for each practice, and the usage report shows them.
`.timing.json` holds the totals of the stage: `durationMs`, `practices`, `positionalHints`, `inDiffHints`, `leads` and `errors`.
`positionalHints` and `inDiffHints` count the hints of positional scripts, and `leads` counts the leads of definition scripts.
`errors` counts the results with the status `error` or `timeout`.

The review runner turns the results into the report `practice-scripts.json` in `out/`, which the server stores.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-report) gives its shape.

## What a script can reach

A practice script is code that a workspace admin writes.
Hephaestus trusts it like the practice definition that it belongs to.
The script still never holds a credential.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-validation-and-limits) gives the grants of the script's process.

The [Node permission model](https://nodejs.org/docs/latest-v24.x/api/permissions.html) is a seat belt, not a sandbox.
It follows symbolic links, and it does not restrict the network.
Thus, a token must not be in a process that runs script code:

| Process | Tokens in its environment |
| --- | --- |
| The container's PID 1 and `pi-practice-scripts.sh` | `LLM_PROXY_TOKEN` and `PRACTICE_SCRIPT_PROXY_TOKEN` |
| `pi-practice-scripts.ts` and `runner.ts`, started with `env -i` | `PRACTICE_SCRIPT_PROXY_TOKEN` only, with `LLM_PROXY_URL` |
| A script's process | None. Its environment is empty. |
| The review runner | `LLM_PROXY_TOKEN` only. The stage unsets `PRACTICE_SCRIPT_PROXY_TOKEN` before the review starts. |

A script's process can read the `/proc/<pid>/environ` of another process only through a symbolic link in a folder that it may read.
No untrusted party can put such a link there:

- The checkout writes each link of the repository as a plain file.
- The server stages context inputs only as regular files.
- The script's process has no write grant.
- The only link in the stage is the fixed `lib` link.

The model calls of a script have these controls:

| Control | Effect |
| --- | --- |
| Model calls through IPC | Each call goes to the runner as a message, and the runner makes it with a credential that the script never holds. |
| Request allowlist | The runner keeps only the fields that a call from a practice script can set. It drops provider options and headers. Chat keeps only function tools. |
| Practice header | The runner names the script's practice on each call. A script cannot name another practice, because the allowlist drops its headers. The [workspace ABI](./agent/workspace-abi.mdx#models-for-practice-scripts) gives the header. |
| No default provider | `lib/models-ipc.ts` sets the AI SDK [global provider](https://ai-sdk.dev/docs/ai-sdk-core/provider-management#global-provider-configuration) to an empty provider, so a script cannot reach another provider through it. |
| Parsed messages | The runner parses every message and result with zod. A message that does not parse stops the script. |

## How the server learns needs

A script declares `meta.models` in code, and the server does not parse scripts.
Thus, the server knows what a script needs only after a review runs it.

The server stores the report of each review attempt as `agent_job_practice_script_run` rows.
The [workspace ABI](./agent/workspace-abi.mdx#practice-script-report) describes the report.
A row holds the status, the number of leads, the declared models, the run time, and the error line of a failed script.
A script whose models are not known has no models in its row.

The job's snapshot holds only the models of its latest attempt.
Thus, a row of an earlier attempt cannot read its tiers from the snapshot.
The row itself stores the tier of the model that the attempt froze for each declared model.
A retry cannot change the tiers of an earlier attempt.
The proxy records the calls and tokens of each slot in an `agent_job_practice_script_usage` row, with the tier of the model that served them.
Thus, a script that did not finish, whose run has no models, still shows the tier of each model that it called.

`GET /workspaces/{workspaceSlug}/agents/jobs/{jobId}/practice-scripts` returns the rows of the current attempt of one review, joined with the usage rows of that attempt.
Only the attempt's terminal write records its rows.
Thus, the list is empty while a retry runs, and a retry never shows the rows of an earlier attempt.

`GET /workspaces/{workspaceSlug}/practices/scripts` serves the needs to workspace admins.
It gives one entry for each practice with a script.
The entry has the needs from the newest run that declared the script's models.
A run whose models are not known says nothing about them, so the server passes over it.
For each need, it names the tiers that no ready assignment serves now.
When that run ran an earlier version of the script, the entry gives `scriptChanged: true` and no needs.

`MemberAiRoutingAdapter.practiceScriptBinding` chooses the model of each slot of a practice script for one developer.
Its ceiling is the stricter of the developer's AI choice and the tier of the review's own model for that developer.
The job's slots and the claim check call it, through `ReviewMemberAiPolicy`.
The needs endpoint calls `unservedTiers` through `PracticeNeedsAdapter`.
`unservedTiers` applies the same ceiling to each member tier, through `serving`.

The LLM proxy does not apply this rule again.
Before each call, it checks only that the model fits the developer's own AI choice.
[Privacy](/admin/ai-providers#privacy) states the rule for admins.

Run one TypeScript file with `node --test <file>`.
`vp run test:agents` runs all of them.
The Java tests run in the server's test tiers (`server/AGENTS.md` § Test tiers).

`test/proxy-stand-in.ts` serves the practice script proxy routes, `POST /practice-script/<slot>/<operation>`.
It checks the practice script token and records each request.
A test gives it a handler that answers by item.
A handler must throw for an item that it does not know, so that a changed prompt fails the test.
A test asserts what the runner guarantees, never the wording of a real model.

To test a new definition script:

1. Put a fixture next to the others in `docker/agents/practice-scripts/fixtures/`.
2. Add a case to `definition.test.ts` that runs the fixture with no models.
   `stagePracticeScripts` stages a requested pull request review beside the fixture, and the test stages `fixtures/pull-request-metadata.json` as its record.
3. Assert the leads that code finds and the `unrated` lines.
4. Add a case for each slot with a stand-in handler that answers by item.
5. Assert the leads, the quotes, and the `models` report in `<slug>.json`.

`validate.ts` runs one script of either contract on a repository without models, through the same staging as the tests.
[Run a script on your own change](/admin/practice-scripts#run-a-script-on-your-own-change) gives its options.

To run a script with models, set `LLM_PROXY_URL` to a server that serves the practice script routes, and `PRACTICE_SCRIPT_PROXY_TOKEN` to its token.
Then pass a models file to `runner.ts` with `--models`.
`live.test.ts` shows this setup with the stand-in.
`fixtures/every-slot.ts` uses every primitive and every slot.
