# Write a practice script

A practice can have a practice script.
The script runs before each review of the practice and points the review at places to check.
This page tells a workspace admin how to write one, try it, and read what it did.

You write the script in the practice editor, in the section **Script**.
It is TypeScript.
The editor saves it with the practice, and the next review of that practice runs it.

## What a script is for

A review checks a practice against the reviewed work.
A script finds the places in the work that the review must look at for that practice.
Such a place is a **lead**: a citation, a kind, and optional facts.
The review reads the leads after the practice's criterion, checks each lead against the criterion, and decides.

A lead is never a claim about the work.
It does not become an observation, and it does not become feedback.
Thus, a wrong lead costs the review one look.
A missing lead costs nothing that the review cannot find alone.

A script can fail, run out of time, or lose its model.
Then the review continues without the script's leads.
The script's section tells the review what was not rated and why.
A failure of a script or a model never becomes a statement about the developer's work.

Most of a script is code.
A script can also call models: a decision model, an embedding model, a reranking model, and the review's own chat model.
Use a model only at a point where code cannot decide.

Every script uses `definePracticeScript`, as this page shows.
A script from an earlier release can have a plain function as its default export.
Hephaestus does not run a script in that retired form.
Its review shows the error *This script uses the retired positional form. Rewrite it with definePracticeScript.*, and continues without the script's leads.
[Rewrite a script in the retired form](#rewrite-a-script-in-the-retired-form) tells how.

## Write your first script

This tutorial writes a script for a practice with this criterion: *Each TODO that the change adds names a tracking item, such as an issue.*

### 1. List the places to look at

Read the criterion.
Then write down the places that a reviewer must look at to judge it:

- Each comment that the change adds and that marks open work, such as a `TODO` or `FIXME`.
- Of those, each comment without a tracking reference: an issue number, a ticket key, or a URL.

Code can find both.
Thus, the first version of the script uses no model.

### 2. Find the places with code

```ts
import { addedComments, definePracticeScript, expectKind, type Lead } from "../lib/practice-script.ts";

const OPEN_WORK = /\b(TODO|FIXME|HACK|XXX)\b/u;
const TRACKING = /#\d+|\b[A-Z][A-Z0-9]+-\d+\b|https?:\/\/\S+/u;

export default definePracticeScript({
  meta: {
    version: 1,
    kinds: { "untracked-todo": "A TODO that the change adds, with no tracking reference." },
  },
  async run(ctx) {
    expectKind(ctx, "scm.pull_request");
    const leads: Lead[] = addedComments(ctx.change)
      .filter((comment) => OPEN_WORK.test(comment.text) && !TRACKING.test(comment.text))
      .map((comment) => ({ at: comment.at, kind: "untracked-todo" }));
    return { leads };
  },
});
```

`expectKind` tells TypeScript that the script reads a pull request, so `ctx.change` exists.
[Narrow the context to a kind](#narrow-the-context-to-a-kind) tells more.
`addedComments` returns each comment that the change adds, with its citation.
`meta.kinds` declares each kind of lead with the sentence that the review reads for it.
The script returns one lead for each comment that marks open work and has no tracking reference.

### 3. Add an optional model

Some temporary work has no marker, such as `// remove before the release`.
Code cannot find it, but a decision model can rate each comment against a fixed set of kinds.
Declare the decision model as `optional`, so that the script still gives its code leads without the model:

```ts
import {
  addedComments,
  classify,
  commentKinds,
  definePracticeScript,
  expectKind,
  type Lead,
} from "../lib/practice-script.ts";

const OPEN_WORK = /\b(TODO|FIXME|HACK|XXX)\b/u;
const TRACKING = /#\d+|\b[A-Z][A-Z0-9]+-\d+\b|https?:\/\/\S+/u;
const NEEDS_A_LOOK = new Set(["untracked-todo", "temporary-stub"]);

export default definePracticeScript({
  meta: {
    version: 1,
    models: { decision: "optional" },
    kinds: {
      "untracked-todo": "A TODO that the change adds, with no tracking reference.",
      "open-work": "An added comment that a model rated as untracked or temporary work.",
    },
  },
  async run(ctx) {
    expectKind(ctx, "scm.pull_request");
    const comments = addedComments(ctx.change);
    const leads: Lead[] = [];
    const unmarked: typeof comments = [];
    for (const comment of comments) {
      if (!OPEN_WORK.test(comment.text)) {
        unmarked.push(comment);
      } else if (!TRACKING.test(comment.text)) {
        leads.push({ at: comment.at, kind: "untracked-todo" });
      }
    }

    const { ratings, unrated } = await classify({
      model: ctx.models.decision,
      set: commentKinds,
      items: unmarked,
      what: "added comments without a TODO marker",
    });
    for (const [comment, rating] of ratings) {
      if (NEEDS_A_LOOK.has(rating.value)) {
        leads.push({
          at: comment.at,
          kind: "open-work",
          rating: { value: rating.value, score: rating.score },
        });
      }
    }

    return { leads, facts: { addedComments: comments.length }, unrated };
  },
});
```

`classify` sends the comments that code did not flag to the decision model.
Code then decides which kinds deserve a lead.
Without a decision model, `classify` returns every comment as not rated, with the reason `unavailable`.
The script returns that `unrated` entry, so the review knows what it must read itself.

### 4. Run it on a change

Run the script on a change of your own before you save it.
[Run a script on your own change](#run-a-script-on-your-own-change) gives the command.
Read the section that the command prints.
It shows each `untracked-todo` lead, and one `Not rated` line for the comments without a TODO marker.

### 5. Save it and assign the model

1. Open the practice in the editor.
2. Open **Script**.
3. Paste the script.
4. Save the practice.
5. Wait for the next review of the practice.
6. If the script uses a model that the workspace has not assigned, open the practice under **Practice setup**.
7. In **Practice script**, follow the link of the model that the script needs.
8. Assign the model, as [Assign a model for practice scripts](./ai-providers.mdx#assign-a-model-for-practice-scripts) tells.

[Which practices use a model for practice scripts](./ai-providers.mdx#which-practices-use-a-model-for-practice-scripts) tells when the needs of a script appear.

## Patterns

Each pattern below gives the case for it, its shape, and what the script gives without its model.
All fragments run inside `run(ctx)` and import from `../lib/practice-script.ts`.
They add to three values that `run` returns at its end:

```ts
const leads: Lead[] = [];
const facts: Facts = {};
const unrated: Unrated[] = [];
```

`comments` is `addedComments(ctx.change)`, after `expectKind(ctx, "scm.pull_request")`.

### Code only

**When:** code can find every place, such as a pattern, a count, or a path.
**Degrades to:** nothing. It needs no model.

The tutorial's first version is this pattern.
Code gives the same leads for the same work, costs nothing, and needs no assignment.
Start each script here.

### Code finds, a decision model filters

**When:** code finds the candidates, and a fixed set of answers decides which candidates deserve a look.
**Degrades to:** the leads that code finds, and one `Not rated` line for the candidates.

```ts
const { ratings, unrated } = await classify({
  model: ctx.models.decision,
  set: commentKinds,
  items: comments,
  what: "added comments",
});
```

The tutorial's second version is this pattern.
`commentKinds` is a complete question set for added comments.
To rate other items, write your own question set, as [`classify` and question sets](#classify-and-question-sets) tells.

### Embeddings for near-duplicates

**When:** you must find items that are almost the same, such as copied comments or near-copies of a function.
**Degrades to:** the leads that code finds, and one `Not rated` line for the compared items.

```ts
const { embedding } = ctx.models;
if (embedding === undefined) {
  unrated.push({ what: "added comments compared for copies", count: comments.length, reason: "unavailable" });
} else if (comments.length > 1) {
  const embedded = await step("embed", async () =>
    embedMany({ model: embedding, values: comments.map((c) => c.text) }),
  );
  if ("unrated" in embedded) {
    unrated.push({ what: "added comments compared for copies", count: comments.length, reason: embedded.unrated });
  } else {
    const vectors = embedded.value.embeddings;
    for (const [i, a] of vectors.entries()) {
      for (const [j, b] of vectors.entries()) {
        const copy = comments[j];
        if (j > i && copy !== undefined && cosineSimilarity(a, b) > 0.9) {
          leads.push({ at: copy.at, kind: "near-copy", facts: { copyOfLine: comments[i]?.at.line ?? 0 } });
        }
      }
    }
  }
}
```

An embedding has no meaning alone.
Compare only vectors from the same model in one run.
Set the threshold in code.

### Rerank to the top N

**When:** code finds more candidates than the review can read, and one description says which matter most.
**Degrades to:** the candidates in the order that code gives, cut to the same N.

`candidates` holds the items that code found, each with its `text`.

```ts
const TOP = 5;
const { reranking } = ctx.models;
let chosen = candidates.slice(0, TOP);
if (reranking !== undefined && candidates.length > TOP) {
  const ranked = await step("rerank", async () =>
    rerank({
      model: reranking,
      query: "temporary or unfinished work that should not be merged",
      documents: candidates.map((c) => c.text),
      topN: TOP,
    }),
  );
  if ("unrated" in ranked) {
    unrated.push({ what: "ranking of the candidates", count: candidates.length, reason: ranked.unrated });
  } else {
    chosen = ranked.value.ranking.flatMap((r) => candidates[r.originalIndex] ?? []);
  }
}
```

A reranking score orders the items.
Do not use it as a rating of an item.

### One structured answer

**When:** one fact about the whole work needs a model, and the answer has a fixed shape.
**Degrades to:** the leads that code finds, without that fact.

```ts
const { chat } = ctx.models;
if (chat !== undefined) {
  const kind = await step("change kind", async () => {
    const { output } = await generateText({
      model: chat,
      output: Output.choice({ options: ["code", "documentation", "configuration", "mixed"] }),
      prompt: `Which kind of change adds these files: ${[...ctx.change.keys()].join(", ")}?`,
    });
    return output;
  });
  if ("value" in kind) {
    facts.changeKind = kind.value;
  }
}
```

Read `output` inside the `step`.
When the answer has no output, reading it throws, and `step` turns the error into `off-format`.
Use `Output.object` with a `z` schema for an answer with more than one field.
The [AI SDK documentation](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data) describes both.

### Locate code with `agent`

**When:** the place is in the repository, outside the change, and finding it needs several searches that code cannot plan.
**Degrades to:** the leads that code finds, without that place.

```ts
const { chat } = ctx.models;
if (chat !== undefined) {
  const found = await step("locate", async () =>
    agent({
      model: chat,
      tools: ctx.tools,
      instructions: "You locate code in a repository. Use the tools to look. Do not guess.",
      prompt: "Find where the function parseDiff is declared.",
      schema: z.object({ file: z.string(), line: z.int().positive() }),
      maxSteps: 8,
      abortSignal: ctx.abortSignal,
    }),
  );
  if ("value" in found) {
    leads.push({ at: { file: found.value.output.file, line: found.value.output.line }, kind: "declaration" });
  }
}
```

Of all primitives, `agent` costs the most.
Give it a narrow question and a small `maxSteps`.
Cite what it found as a `file` lead, so that the runner checks that the lines exist.

### Independent steps together

**When:** a script has two or more steps that do not depend on each other.
**Degrades to:** each step degrades alone.

Write each step as a function that returns its own leads, facts and `unrated` entries.
Start the steps together.
Then join what they return:

```ts
interface Part {
  leads?: Lead[];
  facts?: Facts;
  unrated?: Unrated[];
}

const parts: Part[] = await Promise.all([
  rateComments(ctx, comments),
  findCopies(ctx, comments),
  rankUnfinished(ctx, comments),
]);
return {
  leads: parts.flatMap((part) => part.leads ?? []),
  facts: Object.fromEntries(parts.flatMap((part) => Object.entries(part.facts ?? {}))),
  unrated: parts.flatMap((part) => part.unrated ?? []),
};
```

Then a slow model costs only its own step, and the other steps still finish before the deadline.
Steps that run together share one limit of requests in flight, as [Requests in flight](#requests-in-flight) tells.
To type `ctx` in such a function, declare `meta` as a constant with `as const`.
Then type `ctx` as `PracticeScriptContext<typeof meta.models, "scm.pull_request">`, with the kind that the script reads.

### When not to write a script

Do not write a script in these cases:

- The review can judge the criterion from the change alone, and the change is small.
- Every line of the change is a place to look at. A lead for each line adds nothing.
- Only a model can find the places, and it must read the whole change to do so. The review reads the change already.
- The criterion is about intent, a decision, or a conversation, and no pattern finds the candidates.

## Run a script on your own change

Run the script on a real change before you save it.
The run uses no model, so each model slot is not available.
An `optional` slot then gives `Not rated` lines, and a `required` slot stops the script with the status `skipped`.

You need a checkout of Hephaestus at the version of your instance, and Node.js at the version that the checkout pins.

1. In the checkout, go to `docker/agents/practice-scripts`.
2. Install the dependencies with `pnpm install --frozen-lockfile`.
3. Write the change as a unified diff, for example with `git -C <clone> diff main...HEAD > change.patch`.
4. Run the script:

   ```bash
   node validate.ts --script <script.ts> --repo <clone> --diff change.patch --metadata fixtures/pull-request-metadata.json
   ```

   `fixtures/pull-request-metadata.json` is a sample record of a pull request.
   If the script reads `ctx.work`, copy the sample and put the values of your pull request in it.

5. Read the output.
   It prints the result `<slug>.json` and the section `<slug>.md` that the review reads.
   The command exits with 1 when the script failed or ran out of time.
   It exits with 2 when an option or an input is not valid.
   An example is a `--repo` that is not a folder.
6. Fix the script.
7. Run the command again until the section shows the leads that you expect.

The command accepts these options:

| Option | Value |
| --- | --- |
| `--script` | The script file. Its name, less `.ts`, is the practice's identifier: lowercase letters, digits and hyphens. |
| `--repo` | A checkout of the repository at the head of the change. |
| `--diff` | The change as a unified diff. Without it, the change is empty. |
| `--metadata` | The record of the reviewed work, which the script reads as `ctx.work`. Its shape also sets the kind of the work. [The record of each kind](#the-record-of-each-kind) gives the shapes. Without it, the script fails, because it has no record to read. |
| `--context` | A folder with captured context records, for a script that reads `ctx.context`. |
| `--signal` | A moment, such as `scm.pull_request.merged`. The script runs as a review at that moment. Without it, the script runs as a review that a person requested. |
| `--recheck` | With `--signal`: the script runs as a recheck at that moment. |
| `--cause` | A JSON file with the kind, the subject and the cause, in the shape that the server writes. Use it instead of `--signal` to set the review state or the subject. |
| `--previous` | A JSON file with the previous result, in the shape of [`ctx.previous`](#the-previous-result). If it has a `head` that is an ancestor of the head of `--repo`, the script also gets `changeSince`. |
| `--out` | A folder that keeps `<slug>.json` and `<slug>.md` after the run. |

## Rewrite a script in the retired form

A script in the retired form is a plain function: `(repo, diffFiles, metadata, contextDir, changeDir, contextReference) => ({ hints, metrics, directions })`.
To rewrite it:

1. Wrap the function body in `run(ctx)` of `definePracticeScript`, as [`meta`](#meta) shows.
   Set `meta.version` to `1`.
2. Replace each argument with its field of the context:

   | Argument | Field |
   | --- | --- |
   | `repo` | `ctx.repo` |
   | `diffFiles` | `ctx.change` |
   | `metadata` | `ctx.work` |
   | `contextDir` | `ctx.context.dir` |
   | `changeDir` | `ctx.changeDir` |
   | `contextReference` | `ctx.context.reference` |

   Call `expectKind(ctx, "scm.pull_request")` first when the script reads `ctx.repo`, `ctx.change` or `ctx.changeDir`.
3. Replace each hint with a lead.
   A hint on a changed line becomes `{ at: { change: file, line }, kind }`.
   A hint on a record becomes `{ at: { record: file }, kind }`.
   Declare each kind in `meta.kinds` with one sentence.
   Put the flags of a hint in the `facts` of its lead.
4. Return the metrics as `facts`, and keep the directions.
5. Run the script on a change, as [Run a script on your own change](#run-a-script-on-your-own-change) tells, and save it.

## Use an AI assistant

An AI assistant can write a script from this page.
Give the assistant this page and the brief below.
Replace each «…» with your facts.

```text
Follow the attached guide exactly. Criterion: «…». Places the review must look at: «…». Models this workspace assigns: «…». Return one TypeScript file whose default export is `definePracticeScript({ meta, run })`.
```

1. Copy the criterion from the practice's **What to look for**.
2. List the places, as in [step 1 of the tutorial](#1-list-the-places-to-look-at).
3. List the models for practice scripts that **AI models** assigns. If it assigns none, write `none`.
4. Run the file that you get, as [Run a script on your own change](#run-a-script-on-your-own-change) tells.
5. Give the output back to the assistant until the section is correct.
6. Read the script yourself before you save it. Check it against [Anti-patterns](#anti-patterns).

## Reference

### `meta`

A script has one default export:

```ts
import { definePracticeScript } from "../lib/practice-script.ts";

export default definePracticeScript({
  meta: {
    version: 1,
    models: { decision: "optional" },
    tokens: 20_000,
    kinds: { "untracked-todo": "A TODO without a tracking reference." },
  },
  async run() {
    return { leads: [] };
  },
});
```

The runner reads `meta` before `run` starts.
A `meta` that is not valid stops the script with an error.

| Field | Type | Meaning |
| --- | --- | --- |
| `version` | `1` | Required. The version of the script contract. Version 1 is the leads contract: `run` returns leads, and the review decides what each lead means. A script without it stops with the error `version is missing`. |
| `models` | slot → `"required"` or `"optional"` | The model slots that the script uses. A slot that is not declared is never available. |
| `tokens` | positive integer, at most 500 000 | The token limit of this practice. The default is 20 000. The attempt token limit applies too. [Limits](#limits) gives both. |
| `kinds` | lead kind → one sentence | Each lead kind that the script can return, with the sentence that the review reads for it. |

A kind has 2 to 48 characters and matches `^[a-z][a-z0-9-]{1,47}$`.
Name it by what the place is, such as `untracked-todo`.
Its sentence is one line of at most 300 characters.

### Model slots and needs

A **model slot** is one kind of model that a script can call.

| Slot | AI SDK type | The model that the slot gets |
| --- | --- | --- |
| `chat` | `LanguageModel` | The practice review's own model. You assign nothing for it. |
| `decision` | `Experimental_DecisionModel` | The **Decision model** on **AI models** |
| `embedding` | `EmbeddingModel` | The **Embedding model** on **AI models** |
| `reranking` | `RerankingModel` | The **Reranking model** on **AI models** |

For each review, Hephaestus chooses each model through the reviewed developer's AI choice.
[Privacy](./ai-providers.mdx#privacy) gives the rule.

The runner decides which slots are available before `run` starts:

1. A declared slot is available when the review has a model for it.
2. If a `required` slot is not available, the script does not run. Its status is `skipped`.
3. If an `optional` slot is not available, `ctx.models.<slot>` is `undefined`.

The types follow `meta.models`.
A `required` slot is a model.
An `optional` slot is a model or `undefined`.
An undeclared slot does not exist on `ctx.models`.

Prefer `optional`.
A script with `optional` slots still gives the leads that its code finds when the workspace assigns no model.
Use `required` only when the script has nothing useful to say without the model.

### The context

`run(ctx)` receives one context.
Its shape depends on the kind of the reviewed work.
`ctx.kind` tells the kinds apart.

| Field | What it holds |
| --- | --- |
| `kind` | The kind of the reviewed work: `scm.pull_request`, `scm.issue`, `chat.conversation_thread` or `docs.document`. |
| `work` | The record of the reviewed work. [The record of each kind](#the-record-of-each-kind) gives its fields. |
| `cause` | Why this practice is in this review. [The cause](#the-cause) tells more. |
| `previous` | The previous result of this practice on this work, or `null`. [The previous result](#the-previous-result) tells more. |
| `subject.role` | The role that the practice is about: `AUTHOR`, `REVIEWER` or `MERGER`. |
| `practice.slug` | The identifier of the practice. |
| `context.dir`, `context.reference` | The folder of the captured context, and its reference, to cite records. |
| `now` | The time of the review. Use it instead of the clock. |
| `models` | The available model slots, as AI SDK model objects. |
| `tools` | `readFile`, `listFiles` and `grep` over the repository, as AI SDK tools. |
| `remaining()` | The tokens and milliseconds that this practice has left. |
| `abortSignal` | An `AbortSignal` that aborts shortly before the deadline of this practice. Give it to an AI SDK call as `abortSignal`. |
| `log(text)` | One line to the runner's log. The runner keeps at most 2 000 characters of each line. |

A pull request review also has these fields:

| Field | What it holds |
| --- | --- |
| `repo` | The absolute path of the repository checkout at the reviewed head. |
| `change` | The parsed change: path → added and removed lines, keyed by line number. |
| `changeDir` | The folder of the change view: `diff.patch`, `diff_stat.txt` and `files.json`. The local command gives an empty string. Prefer `change`. |

#### Narrow the context to a kind

A practice reviews one kind of work: the kind of its moments.
Call `expectKind` before you read a field of that kind:

```ts
async run(ctx) {
  expectKind(ctx, "scm.pull_request");
  const comments = addedComments(ctx.change);
  // …
}
```

After `expectKind`, TypeScript knows the kind of `ctx`, so `ctx.change` and the fields of `ctx.work` exist.
If the review is about another kind, `expectKind` throws.
The script then fails with the status `error`.
It never reports that it found nothing.
A script that reads more than one kind uses `switch (ctx.kind)` instead.

#### The record of each kind

The runner reads the record of the work from the context folder and validates it before the script starts.
`ctx.work` holds only the fields below.
If the record does not have this shape, the script does not run, and its status is `error`.

| Kind | Record | `ctx.work` |
| --- | --- | --- |
| `scm.pull_request`: a GitHub pull request or a GitLab merge request | `metadata.json` | `pr_number`, `pr_url`, `repository_full_name`, `source_branch`, `target_branch`, `commit_sha` (the reviewed head), `subject_role`, `is_draft`, `is_merged`, `additions`, `deletions`, `changed_files`, `labels`, `assignees`, and `basis`, which tells when each field was read. When they are known: `title`, `body`, `state`, `created_at`, `closed_at`, `merged_at`, `author`, `author_id`, `author_bot`, `merged_by`, `milestone`, `merge_state_status`, `review_decision` and `head_checks`. |
| `scm.issue`: a GitHub or GitLab issue | `metadata.json` | `issue_number`, `title`, `body`, `state`, `state_reason`, `html_url`, `repository_full_name`, `author`, `author_id`, `issue_type`, `is_locked`, `sub_issues_total`, `sub_issues_completed`, `milestone`, `closed_at`, `labels` and `assignees`. `sub_issues_source` when the counts are known. A field that the provider did not record is `null`. |
| `chat.conversation_thread`: a Slack thread | `conversation_thread.json` | `channel`, `threadTs`, `messages`, `messageCount` and `truncated`. Each message has `ts`, `author` and `text`. When they are known, it also has `authorLogin`, `authorName`, `underReview` and `edited`. |
| `docs.document`: an Outline document | `document.json` | `title`, `collection`, `collectionSlug`, `slug`, `createdBy`, `updatedBy`, `createdAt`, `updatedAt` and `archived`. The body is `document.md` in `context.dir`. |

A descriptive field can get a value that this release does not know, such as a new pipeline state from a provider.
Then `head_checks` and `sub_issues_source` are absent, which means that they are not known, and the `state` of an issue is `UNKNOWN`.
A value of another shape in any other field fails the record.

[Pull request records](/contributor/agent/agent-workspace-abi#pull-request-records) gives the meaning of each field of a pull request.

#### The cause

The moments and the review conditions of a practice are its review occasion.
`ctx.cause` tells the script which of them brought the practice into this review, or that a recheck or a request by hand did.
`ctx.cause.type` has one of three values:

| `type` | Meaning | Fields |
| --- | --- | --- |
| `moment` | The practice is bound to the moment of the review, and its review conditions match. | `signal`, `origin`, `state`, `admittedAt`. On `scm.pull_request.reviewed`, also `review`. |
| `recheck` | The practice's current result about the author is not met, and the work changed after that result. The practice is not bound to the moment. | `signal`, `origin`, `state`, `admittedAt` |
| `requested` | A person asked for a review, or an admin started a review of earlier work. Each practice of the kind runs, in any state. | `origin`, `state`, `admittedAt` |

- `signal` is the moment that the review was admitted under. It has the same name as in the practice's moments, such as `scm.pull_request.merged`.
- `origin` is `LIVE`, `MANUAL` or `BACKFILL`, as [How a review was occasioned](/contributor/practice-review-glossary#how-a-review-was-occasioned) tells.
- `state` is the state of the work that the review recorded when Hephaestus admitted it, such as `{ state: "OPEN", draftStatus: "NOT_DRAFT" }`. A conversation has no state.
- `admittedAt` is the time when Hephaestus admitted the review.
- `review` has the `id` of the submitted review and the login of its `reviewer`.

| Kind | Moments |
| --- | --- |
| `scm.pull_request` | `opened`, `ready`, `synchronized`, `edited`, `reviewed`, `merged`, `closed`, and `linked_issue_updated`, which only a recheck has |
| `scm.issue` | `opened`, `updated`, `closed` |
| `chat.conversation_thread` | `settled` |
| `docs.document` | `published`, `updated`, `archived` |

Each moment has the kind as its prefix, such as `scm.issue.closed`.

#### The previous result

`ctx.previous` is the latest current result of this practice about the same person on this work.
It is `null` when there is none.

| Field | What it holds |
| --- | --- |
| `reviewedAt` | The time of that result. |
| `cause`, `signal` | Why that review ran: `moment`, `recheck` or `requested`, as in [the cause](#the-cause). |
| `outcome` | `MET`, `NOT_MET`, `NOT_APPLICABLE` or `UNDETERMINED`. |
| `severity` | For `NOT_MET`: `CRITICAL`, `MAJOR`, `MINOR` or `INFO`. |
| `citations` | The places that the result cites: `sourceKind`, `path`, `startLine`, `endLine`, and `side` for a line of the change. |
| `head` | For a pull request: the head that the earlier review read. |
| `changeSince` | For a pull request: the change from `head` to the reviewed head, in the shape of `change`. It is absent when `head` is not an ancestor of the reviewed head, for example after a force push. An empty map means that nothing changed. |

`previous` has no summary and no rationale, because a model wrote them.
It has no delivery state.
A result that an admin marked incorrect is not a current result.
A result whose evidence the workspace no longer permits is not a current result either.

The runner marks each lead on a line that `changeSince` adds.
[What the review reads](#what-the-review-reads) tells how.

#### The practice decides when it runs

The moments and the review conditions of the practice decide when the practice is reviewed.
The script does not decide it.
Read `ctx.cause` to do different work at different moments.
Do not read fields such as `work.is_merged` to find out if the moment came.
If a practice must not run at a moment, remove the moment from the practice.

#### Different work for each cause

This script does different work on a request, a recheck, a push and a merge:

```ts
import {
  addedComments,
  definePracticeScript,
  expectKind,
  type DiffFile,
  type Lead,
} from "../lib/practice-script.ts";

const OPEN_WORK = /\b(?:TODO|FIXME)\b/u;
const TRACKING = /#\d+|\b[A-Z][A-Z0-9]+-\d+\b|https?:\/\/\S+/u;

export default definePracticeScript({
  meta: {
    version: 1,
    kinds: { "untracked-todo": "A TODO that the change adds, with no tracking reference." },
  },
  async run(ctx) {
    expectKind(ctx, "scm.pull_request");
    const todos = addedComments(ctx.change).filter(
      (comment) => OPEN_WORK.test(comment.text) && !TRACKING.test(comment.text),
    );
    // The leads in the files of `only`, or in the whole change.
    const leads = (only?: ReadonlyMap<string, DiffFile>): Lead[] =>
      todos
        .filter((comment) => only === undefined || only.has(comment.at.change))
        .map((comment) => ({ at: comment.at, kind: "untracked-todo" }));

    const { cause } = ctx;
    if (cause.type === "requested") {
      return {
        leads: leads(),
        directions: ["A person asked for this review. Judge the work as it is now."],
      };
    }
    if (cause.type === "recheck") {
      return {
        leads: leads(),
        directions: ["The last review found untracked TODOs. Check if the new commits track them."],
      };
    }
    if (cause.signal === "scm.pull_request.synchronized") {
      // Only the files that the new commits changed, when that change is known.
      return { leads: leads(ctx.previous?.changeSince) };
    }
    if (cause.signal === "scm.pull_request.merged") {
      return {
        leads: leads(),
        directions: ["The work is merged. Each untracked TODO is now on the target branch."],
      };
    }
    return { leads: leads() };
  },
});
```

`docker/agents/practice-scripts/fixtures/by-cause.ts` holds the same script, and its tests run it.
The script does not list its moments.
If an admin removes `merged` from the practice, the `merged` branch does not run again.
On `opened`, `ready` and `edited`, the last `return` runs.

### Primitives and tools

`../lib/practice-script.ts` is the one library import of a script.
It exports `definePracticeScript`, the primitives below, the reader `addedComments`, the question set `commentKinds`, and the types.

| You need to | Use | Slot | Calls |
| --- | --- | --- | --- |
| Find a pattern, count lines, or match a path | Plain TypeScript and the readers | none | none |
| Rate many items against a fixed set of answers | `classify` with a question set | `decision` | One for each pack of 30 items |
| Find items that are almost the same | `embedMany` and `cosineSimilarity` | `embedding` | One for each 64 values |
| Find the items closest to one description | `rerank` with at most 256 documents | `reranking` | One |
| Get one structured answer about the work | `generateText` with `Output` | `chat` | One |
| Find something that needs several searches in the repository | `agent` with `ctx.tools` | `chat` | Up to `maxSteps` |
| Contain a failure and label its model calls | `step` | any | none |

#### `step`

`step(label, run)` runs one unit of work.
It returns `{ value }`, or `{ unrated: reason }` when the work throws.
When a model call in the step fails, the runner's log names the label.
A nested step joins the labels with `›`.

Put each model call that is not in `classify` inside a `step`.
Then one failure leaves one unit not rated, and the rest of the script continues.

#### `classify` and question sets

`classify({ model, set, items, what })` rates items through a decision model.
`set` is a `QuestionSet` with these fields:

| Field | Meaning |
| --- | --- |
| `name` | The name of the vocabulary, such as `comment kind`. |
| `noun` | What one item is, such as `added code comment with the code around it`. |
| `question` | The question for each item. |
| `values` | Value → definition. A value has the shape of a lead kind, such as `restates-code`. |
| `render` | The item as the model reads it. |

`classify` tells the model that the items are data, and that instructions inside an item are part of the data.
It returns a `Rating` for each item that the model answered: `value`, `score` and `probabilities`.
Every other item is in `unrated`:

- If the model is `undefined`, all items are not rated, with `unavailable`.
- If a call fails, all items of its pack are not rated, with the reason of the failure.
- If the model answers an item in a form that is not valid, that item is not rated, with `off-format`.

#### `agent` and the repository tools

`agent` runs a bounded AI SDK `ToolLoopAgent` that reads the repository and answers with your schema.

- It must call a tool at each step.
- It answers through a final `submit` tool with your schema.
- It stops at `submit` or after `maxSteps` steps. The default is 8.
- Without a model, it throws `UnratedError` with `unavailable`.
- Without a `submit` call, it throws `UnratedError` with `budget`.

`ctx.tools` holds three read-only tools:

| Tool | Limit |
| --- | --- |
| `readFile` | 200 numbered lines for each call. It does not read a file larger than 2 MiB. |
| `listFiles` | 200 entries |
| `grep` | 50 matches |

`readFile` and `listFiles` refuse a path outside the repository.

#### Other model calls

`generateText` sets the temperature to 0 when the call does not set it.
`streamText` is not available.
A string model ID fails, so a script reaches a model only through `ctx.models`.
A model call runs once.
Nothing retries it.

### Result and citations

`run` returns this value:

| Field | Limit | Meaning |
| --- | --- | --- |
| `leads` | 200 | Places to look at. |
| `facts` | 32 keys | Facts about the whole work, such as a count. |
| `unrated` | 20 entries | What the script could not rate, how many, and why. |
| `directions` | 10 lines of 300 characters | Instructions to the review. Write them yourself. Never pass model text. |

A lead has these fields:

| Field | Meaning |
| --- | --- |
| `at` | The citation. |
| `kind` | A kind that `meta.kinds` declares. |
| `facts` | Optional facts about this place. |
| `rating` | Optional `{ value, score }` from a model. `value` has the shape of a lead kind. `score` is from 0 to 1. |

A fact is a one-line string of at most 200 characters, a finite number, or a boolean.
Its key has at most 64 characters, starts with a letter, and has only letters and digits, such as `similarCommentPairs`.

A citation has one of three shapes:

| Shape | Points at |
| --- | --- |
| `{ change, line, endLine?, side? }` | Lines that the change adds (`NEW`, the default) or removes (`OLD`) |
| `{ file, line, endLine? }` | Lines of a file in the repository |
| `{ record, line? }` | A captured record in the context folder. Line 0 or no line cites the whole record. |

An `unrated` entry is `{ what, count, reason }`.
`what` names the items for the review, such as `added comments`, in at most 160 characters.

### How leads are settled

The runner settles each lead before the review sees it:

1. It drops a lead whose kind `meta.kinds` does not declare.
2. It drops a lead whose citation the source does not hold.
   A quote spans at most 20 lines, and a quoted file has at most 2 MiB.
3. It writes the quote of each lead that it keeps, from the source.
   A script never writes a quote.
4. It counts the dropped leads and shows them as one `Not rated` line with `off-format`.

### Reasons

A reason tells why something was not rated.
It never means "nothing found".
A script uses one of seven reasons: `unavailable`, `budget`, `deadline`, `too-large`, `off-format`, `refused` and `error`.
[Calls that were not rated](./practice-review-operations.mdx#calls-that-were-not-rated) gives the meaning of each reason and what to do.
It also tells which reasons the review's pages show.

`reasonOf(error)` maps an error to a reason.
`step` and `classify` use it.
`UnratedError` carries the reason of a call that the runner refused or could not finish.

### Limits

| Limit | Value |
| --- | --- |
| The token limit of the practice | `meta.tokens`, default 20 000 |
| The attempt token limit: the tokens of one review attempt, all scripts together | Default 200 000. [Cost and limits](./ai-providers.mdx#cost-and-limits) tells who sets it. |
| The attempt search unit limit: the search units that reranking calls of one review attempt billed, all scripts together | Default 1 000. Only the proxy counts search units, so a call that it refuses is not rated, with `budget`. |
| Model calls in flight, all scripts together | 4 |
| Requests in flight from one script: model calls and `ctx.tools.grep` searches | 32. One more stops the script with an error. |
| Output tokens of one chat call | 4 096 |
| Entries in one call | 64 decision questions, 64 embedding inputs, 256 reranking documents |
| Time | The deadline of each script and of the stage, in the [workspace ABI](/contributor/agent/agent-workspace-abi#practice-script-validation-and-limits) |

Read `ctx.remaining()` before an expensive step.
Pass `ctx.abortSignal` to long work, such as `agent`.

#### Requests in flight

A script that sends more than 32 requests at the same time stops with an error.
The runner sends only 4 model calls at a time, so the other requests wait in the runner.
Some primitives send many calls at once:

- `classify` sends at most 4 packs of 30 items at the same time, so it does not stop the script.
- `embedMany` sends all its calls of 64 values at the same time.
  Thus, more than 2 048 values in one `embedMany` stop the script.
  Set `maxParallelCalls` on `embedMany` to send fewer calls at a time.
- `Promise.all` over model calls or `grep` sends all of them at once.

Cut a large set of items into parts.
Send the next part only after the previous part is complete.

#### Token reservations

The runner reserves tokens for each model call before the call starts.
A call waits for its turn among the 4 calls in flight, and then makes its reservation.
If the token limit of the practice or the attempt token limit cannot hold the reservation, the call is not rated, with `budget`.
When the call ends, the runner keeps only the tokens that the provider reported, and frees the rest.
A call can report more tokens than its reservation, so the stage can end above a token limit.
A call that fails, is cancelled, or reports no tokens keeps its whole reservation.

A reservation is one token for each four characters of the request, plus an output allowance:

| Call | Output allowance |
| --- | --- |
| Chat | Its `maxOutputTokens`, at most 4 096. Without it, 4 096. |
| Decision | 12 tokens for each question, plus 16 |
| Embedding or reranking | 64 tokens |

Thus, with the default 20 000 tokens, a practice can hold only a few chat calls in flight at the same time.
Set `maxOutputTokens` on a chat call to the length that its answer needs.
Raise `meta.tokens` for a script that makes many chat calls.

### What the review reads

The runner turns the result into one section, which the review reads after the practice's criterion.
The section holds these lines:

- The directions.
- The sentence of each lead kind that the section shows, once.
- For each lead: its kind, its place, the first line of its quote, and its facts as `key=value`.
- `(model-rated)` after the kind of a rated lead. The review never sees the score or the rated value.
- When [`changeSince`](#the-previous-result) is known, one line that counts the leads on lines added after the last review.
  An example is `1 of 2 leads point at lines added since the last review of this practice, each marked (new).`
  Each such lead has `(new)` after its kind.
- The facts about the whole work.
- One `Not rated` line for each `unrated` entry, such as `Not rated: 3 added comments (unavailable). Read those yourself.`

A section has at most 3 000 characters, so one script cannot push the leads of another practice out.
The notices come first in this bound: the notice of a failed script and the `Not rated` lines.
They take at most 1 500 characters.
When more `Not rated` lines exist, one line counts the entries that the section does not show.

The directions, the leads and the facts get the rest of the bound, in that order.
When they do not fit, the section keeps the first lines.
Then one line counts the lines that the section does not show, and how many of them are leads.
That line points to the full result.
Thus, return only the leads that the review needs.

If the script fails or runs out of time, the section says so, and the review assesses the practice from the sources.
If the script does not run because a `required` slot is not available, the section names the slots.

## Anti-patterns

| Do not | Do this instead | Reason |
| --- | --- | --- |
| Ask a model what code can compute | Compute it, and use the model only for the judgment. | Code is free, gives the same answer each time, and needs no assignment. |
| Ask a model whether the practice is met | Return places. | The review judges against the criterion. A script that judges hides its evidence. |
| Pass model text into `directions`, `facts`, or a kind | Map the answer to a declared kind or a fact. | Model text in the review's turn can carry instructions from the work. |
| Return no leads when a model was not available | Return the `unrated` entries that `classify` or `step` gives. | An empty list alone tells the review that nothing was found. |
| Use `required` when code alone finds useful leads | Use `optional`. | A workspace without the model still gets the code leads. |
| Read `Date.now()` or `Math.random()` | Use `ctx.now`. Keep the output a function of the input. | The same work must give the same leads. |
| Send the whole repository to `agent` | Give it a narrow question and a small `maxSteps`. | Of all primitives, `agent` costs the most, and the deadline is short. |
| Cite a file when you mean one line | Cite the line or the smallest range. | The review reads the first line of the quote. |
| Catch an error and return an empty result | Let `step` turn it into a reason. | The review must know what it must read itself. |
| Name a lead kind by a verdict, such as `violation` | Name it by what the place is, such as `untracked-todo`. | A lead is a place, not a claim. |
| Ask for a model by name | Use `ctx.models`. | The workspace owns the assignment and its data handling. |
| Read `work.is_merged` or `work.state` to find out if the moment came | Read `ctx.cause`. Change the practice's moments and review conditions. | The practice decides when it is reviewed. A second rule in the script goes out of date. |
| Return no leads for a kind of work that the script does not read | Call `expectKind`. | A wrong kind is an error of the script, not a review that found nothing. |
