# Write a practice

State a positive standard that a review can judge within a clear evidence boundary.
Describe required behavior once. Keep guidance separate from the criteria.

## Define the standard

1. Enter the practice's name and stable identifier.
2. Select its kind of work.
3. Write what the work must do to meet the practice.
4. Describe the facts that make the practice inapplicable.
5. Describe the consequence that justifies each problem's severity.

An optional improvement is not a problem.
A broad claim needs evidence for its full boundary.
A search can prove absence only within a complete bounded corpus.
The [outcome contract](/contributor/practice-feedback-language#result-outcomes) owns the four verdicts.

## Select review evidence

Review on selects events. When selects their recorded state for automatic review.
Applies when governs every origin, including a request.
A request does not bypass source access, scope or consent.

About selects Author, Reviewer, Assignee or Merger.
Choose The work when the result concerns no developer.
A selected role must resolve to one eligible human account.
A missing or ambiguous role withholds the practice instead of choosing a person.

Reads retains the source contract and required, complete or optional sources.
Required capture failure never becomes a semantic outcome.
Do not list optional evidence as sufficient proof of exhaustive coverage.

## Choose who reviews

Reviewed by has three choices:

- Hephaestus: automated review within the declared evidence boundary.
- People: human review, with the reason automation cannot decide.
- Nobody: guidance without automated review.

Keep the human reason and known limits with this choice.
Do not duplicate them in a second rubric.
Feedback mode is a separate delivery setting. Off does not stop eligible result recording.

## Add a script and scan support

A null Script uses the built-in script.
A custom script can prepare model review or decide from exact captured records.
The [script guide](./practice-scripts.mdx) owns its author contract and tests.
An invalid custom script never falls back silently.

Scan support declares selected files and context explicitly.
It is available only for practices with a valid repository-state form.
A duty at a change event cannot gain a scan form by ignoring that event.
A scan result concerns the file and has no developer.

## Write guidance

Why it matters explains the practice's purpose.
What good looks like describes work that meets it.
Going well describes what the developer keeps doing when supported results establish that pattern.
Visual and Guide use the existing validated picture and Markdown controls.
Guidance does not add a new criterion or change the evidence standard.

## Save or reset

Saving a changed definition creates a fixed practice version.
Earlier results retain their original definition.
A name, group or guidance change does not change the review standard digest.
Reuse still requires the exact practice version and method.
Reset removes local customization through the catalog comparison.
Check the displayed changes before resetting.
