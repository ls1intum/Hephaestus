# Observability contract

Every runtime role writes one JSON record per event to standard output.
Spring Boot writes the records in its built-in [Elastic Common Schema (ECS) format](https://docs.spring.io/spring-boot/reference/features/logging.html#features.logging.structured).
`job.id` and `workspace.id` are fields, not metric labels.
The application exports no logs.
The container runtime keeps them on the host until an operator collects them ([Collecting logs](#collecting-logs)).

## Scrape metrics

Each runtime role serves `GET /actuator/prometheus` without a user token on a separate management
listener, port **9090** by default (`MANAGEMENT_PORT` outside the supported Compose stacks). The
application listener refuses this metrics path, including requests with a user token. Port 8081 is
the sandbox gateway, not a metrics endpoint. Liveness and readiness also remain available on the
application listener at `/livez` and `/readyz`. Container probes use these application-listener paths.

The reference and single-host Compose stacks bind management to the container's own `shared-network` address through its network-qualified hostname.
They expose 9090 **only on that network**.
This excludes sandbox interfaces, including after a restart with other networks attached.
Docker's [network-scoped DNS resolution](https://github.com/moby/moby/blob/v28.2.2/libnetwork/sandbox.go#L401-L425) selects the management network without a fixed container IP.
The stacks do not publish the management port to the host or configure a proxy route.

Docker `expose` is not a firewall.
Any container on that network can read metrics.
The management listener's default address is loopback (`127.0.0.1`).

1. Attach your own Prometheus to that network.
2. Do not add a `ports` mapping, Traefik router, or internet ingress for management.
3. Restrict network membership to trusted services.
4. For non-Compose deployments, restrict the management listener with private networks and firewall policy before startup.
5. For a remote scraper, set `MANAGEMENT_SERVER_ADDRESS` to a specific trusted private interface.
6. Do not use the application or sandbox gateway port for management.

See [Spring Boot management listeners](https://docs.spring.io/spring-boot/reference/actuator/monitoring.html) and [Prometheus security](https://prometheus.io/docs/operating/security/).

No monitoring service or outbound metric exporter is enabled by this configuration. Operators who
do not run Prometheus need no monitoring setup. Traces remain opt-in and separate from scraping.

Example `prometheus.yml` for the reference deployment:

```yaml
scrape_configs:
  - job_name: hephaestus
    scrape_interval: 30s
    scrape_timeout: 10s
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: [application-server:9090]
        labels:
          runtime_role: server
      - targets: [application-worker:9090]
        labels:
          runtime_role: worker
      - targets: [webhook-server:9090]
        labels:
          runtime_role: webhook
rule_files:
  - hephaestus-alerts.yml
```

For multiple replicas:

1. Discover and scrape **all containers**, not a load-balanced service address that can switch replicas between scrapes.
2. Keep each target's `instance` label distinct.
3. Apply `increase` or `rate` to each counter before you sum them.
4. Never add `workspace.id` or `job.id` as metric labels.

This handles resets per process.
`runtime_role` above is an operator-supplied target label, not an application meter label.
`workspace.id` and `job.id` remain log fields.

### Example alert rules

These rules use the **exported Prometheus names**, not the dotted Micrometer names. The receiver
exports stream poll age. Server consumers export poison counts. Budget admission and committed
agent-job outcomes can occur in different roles, so their rules aggregate all scraped roles.

The poll-age threshold is three times the default 60-second monitor interval.
A failed scrape and a missing poll-age series are separate alerts.
`NaN` means a stream has never been polled successfully, not that its age is zero.

1. Use the rules below as `hephaestus-alerts.yml`.
2. Adjust windows, thresholds, and routing to your traffic and recovery objectives.
3. If you change the monitor interval, increase the poll-age threshold.

```yaml
groups:
  - name: hephaestus
    rules:
      - alert: HephaestusMetricsUnavailable
        expr: up{job="hephaestus"} == 0
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: A Hephaestus metrics target cannot be scraped
      - alert: HephaestusConsumerPoison
        expr: sum by (kind) (increase(integration_consumer_poison_total{job="hephaestus"}[10m])) > 0
        labels:
          severity: warning
        annotations:
          summary: An integration event reached the poison retry limit
      - alert: HephaestusStreamPollStale
        expr: >-
          webhook_stream_poll_age_seconds{job="hephaestus",runtime_role="webhook"} > 180
          or webhook_stream_poll_age_seconds{job="hephaestus",runtime_role="webhook"}
          != webhook_stream_poll_age_seconds{job="hephaestus",runtime_role="webhook"}
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: Webhook stream gauges are stale or have never been refreshed
      - alert: HephaestusStreamPollMissing
        expr: >-
          up{job="hephaestus",runtime_role="webhook"} == 1
          unless on (job, instance)
          webhook_stream_poll_age_seconds{job="hephaestus",runtime_role="webhook"}
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: A scraped webhook receiver exports no stream poll age
      - alert: HephaestusBudgetExhausted
        expr: sum(increase(llm_budget_exhausted_total{job="hephaestus"}[10m])) > 0
        labels:
          severity: warning
        annotations:
          summary: A workspace crossed the instance-funded monthly budget cap
      - alert: HephaestusBudgetBlocked
        expr: sum by (surface, cap) (increase(llm_budget_blocked_total{job="hephaestus"}[10m])) > 0
        labels:
          severity: warning
        annotations:
          summary: LLM budget admission refused work
      - alert: HephaestusAgentJobsFailing
        expr: sum(increase(review_job_total{job="hephaestus",outcome=~"failed|timed_out"}[15m])) >= 3
        labels:
          severity: warning
        annotations:
          summary: At least three agent jobs failed or timed out in fifteen minutes
```

1. Enable stream rules only where you expect the webhook stream monitor.
2. To detect an individually missing stream, add an `absent_over_time` rule for each expected `stream` and receiver target.

   The example missing-series rule detects loss of the whole monitor.
   Counters created on their first event can be absent before that event.
   An `increase` rule needs at least two samples.
   It cannot recover an event that occurred before its first sample.
   Scraping does not replace warning and error logs.

   Poison counts mean the application stopped retrying a delivery.
   They are not a durable dead-letter queue.
   Failed outcomes exclude deliberate cancellation.
   See [Webhook ingestion operations](./webhook-ingestion-operations.mdx#what-to-alert-on) and [Alert response](./production-operations-runbook.mdx#alert-response) for response steps.

3. Validate the config with:

   ```bash
   promtool check config prometheus.yml
   ```

4. Validate the rules with:

   ```bash
   promtool check rules hephaestus-alerts.yml
   ```

5. Before relying on them, test rule evaluation in your monitoring stack.
6. Before relying on the rules, test the notification route.

Prometheus evaluates rules.
Your Alertmanager or equivalent controls notification delivery, grouping, and silences.
See the [Prometheus alerting guidance](https://prometheus.io/docs/practices/alerting/).

## Reading log records

| Field                                             | Meaning                                                                                          |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `@timestamp`                                      | UTC event time, in ISO-8601 format                                                               |
| `log.level`, `log.logger`, `message`              | Severity, originating logger, and human-readable event description                               |
| `service.name`, `service.version`                 | `Hephaestus` and the running version, the same values that traces carry                          |
| `service.environment`                             | `DEPLOYMENT_ENVIRONMENT`                                                                         |
| `service.node.name`                               | The container ID, the same value as the `X-Hephaestus-Replica` response header                   |
| `runtime.role`                                    | `server`, `worker` or `webhook`, or `all` for a local process that runs every role               |
| `context.event.name`                              | Stable name on structured application events. Do not parse the message to identify these events  |
| `context.traceId`, `context.spanId`               | The active trace scope, when there is one                                                         |
| `context.job.id`, `context.workspace.id`          | Thread-scoped context, when available                                                            |
| `context.installation_id`                         | The GitHub App installation of a workspace-scoped request, when it has one                      |
| `context.integration.route`, `context.integration.delivery` | On `integration.message.failed`: provider and event (`github.push`), and the delivery count |
| `context.*`                                       | Every other event field and thread-scoped value                                                  |
| `error.type`, `error.stack_trace`                 | Exception class and frames when a call site includes the exception. Not present on every failure |

Spring Boot writes a dotted name such as `log.level` as nested JSON objects.
Event fields and thread-scoped values sit in the `context` object, so they cannot replace a field of the record.
This document names them without the `context.` prefix below.
Read records with a JSON tool, not by text position.
Event-specific numbers and booleans remain JSON numbers and booleans.

A JSON string can contain escaped newlines.
Read logs as JSON, not as extra records from their rendered text.

A stack trace is at most 8192 characters and at most 32 frames for each exception.
Docker splits a log line at 16 KiB, and the pieces are not JSON, so one record must stay below that.
JSON escaping makes the written trace slightly longer than its limit.
A message that a call site writes has no limit of its own.
Each exception line carries a hash, so you can count repeated failures of one kind.

A record names each exception in a stack trace, including causes and suppressed exceptions, by its class only.
It contains no `error.message`.
A database driver quotes rejected row values in its messages, an HTTP client the request URL, and a parser the input that it rejected.
These boundaries have their own guard:

- The PostgreSQL driver runs with `logServerErrorDetail=false`, so its messages omit the `DETAIL` line that quotes rejected row values.
  The primary message, the SQLSTATE and the constraint name remain.
  A primary message can still quote a value for some kinds of error.
- Hibernate's own log of the driver message for a failed statement, the `org.hibernate.orm.jdbc.error` category, is off.
  The application still logs the exception class and frames, and conflicts still record the SQLSTATE.
- Tomcat's request parser, `org.apache.coyote.http11.Http11Processor`, logs at `WARN` and above only.
  At `INFO` and `DEBUG` it writes the raw target of a request that it cannot parse, query string included.

The application writes an exception's class, not its message, into its own log messages.
Sync, provider, webhook and NATS failures log the class with the operation, the status where known, and opaque identifiers.
A failed NATS delivery logs its route and delivery count, and attaches the stack trace on the first delivery only.
The subject, which names an owner and a repository, stays out of the record.
Workspaces are identified by `workspace.id`. The workspace slug is not a log field.

Run production at `INFO`.
`DEBUG` on framework, client or driver packages can write request content, provider responses and container settings that no guard above covers.

The startup event `runtime.roles.configured` records `runtime.server.enabled`,
`runtime.worker.enabled`, and `runtime.webhook.enabled` as booleans. It is informational when any
role is enabled and warns when all are disabled. A role configuration log is not a readiness probe.

At the shared HTTP boundary, `integration.request.failed` identifies the request method, upstream
host, and exception class without recording the full URL, headers, or exception message.
`database.constraint.conflict` identifies the exception class and a valid five-character SQLSTATE
(`db.response.status_code`) without recording SQL or rejected row values. Both remain warnings.
The response still reports service unavailability or a conflict.

GitLab webhook registration failures expose the workspace and HTTP status in
`integration.webhook.registration.failed`, never the provider's response body. Outline request
diagnostics use `integration.request.failed` with the API operation, host, exception type, and HTTP
status when available. They stay at debug level and do not include raw transport/decoding messages.

When a review sandbox fails, the log records the size of its transcript as `sandbox.transcript.withheld`, not its content.
The transcript holds what the run was asked, what it read and the provider errors that it saw.
No log level writes it.
For a next-day investigation, use the worker's bounded debug session transcripts ([retention decision](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0041-compose-1x-kubernetes-2.md#update--2026-10-09-debug-transcripts)).

The formatter masks secret field names (for example `token`, `authorization`, `PRIVATE-TOKEN`, `X-Gitlab-Token` and `privateKey`) and known credential formats.
These formats are bearer and basic credentials, GitHub, GitLab and Slack tokens (including `xoxe-` and `xapp-`), JWTs, credentials in a URL, and signed or token query parameters.
This masking is defense in depth, not redaction.
It does not detect names, email addresses or private text that a call site writes into a message.

Keep raw requests, provider responses, signed URLs, and private runtime text out of logs.
Restrict log access and retention as part of the instance's data-protection policy.
Identifiers such as `workspace.id`, `job.id`, a trace ID or a container ID are not anonymous.
They connect records to a workspace and its people, so they are personal data under the same policy.

## Agent-job lifecycle

Lifecycle records contain `event.name`, `job.id`, `workspace.id`, `job.type`, `job.phase`,
`job.outcome`, and `duration.ms`.

| `event.name`         | Emitted when                  | `job.phase` | `job.outcome`                                   | `duration.ms`                 |
| -------------------- | ----------------------------- | ----------- | ----------------------------------------------- | ----------------------------- |
| `agent.job.queued`   | A new job transaction commits | `queue`     | `queued`                                        | `0`                           |
| `agent.job.started`  | A worker starts a claimed job | `queue`     | `started`                                       | Creation to start             |
| `agent.job.delivery` | A delivery attempt finishes   | `delivery`  | `delivered`, `failed`                           | Delivery attempt              |
| `agent.job.terminal` | A terminal transition commits | `total`     | `completed`, `failed`, `timed_out`, `cancelled` | Creation to terminal emission |

Delivery is optional. Jobs that do not complete successfully may have no delivery event.

## Agent-job metrics

| Prometheus name               | Type      | Labels    | Meaning                                                         |
| ----------------------------- | --------- | --------- | --------------------------------------------------------------- |
| `review_job_total`            | Counter   | `outcome` | Committed terminal transitions                                  |
| `review_job_duration_seconds` | Histogram | `phase`   | Queue, execution-attempt, delivery-attempt, and total durations |

`outcome` is one of `completed`, `failed`, `timed_out`, or `cancelled`. `phase` is one of `queue`,
`execution`, `delivery`, or `total`. Identifiers, model and provider names, worker IDs, and exception text are not
labels. See [Practice Review Operations](./practice-review-operations.mdx) for queue health and the
existing execution metric.

## Heph turn metrics

| Prometheus name                   | Type      | Labels    | Meaning                                                         |
| --------------------------------- | --------- | --------- | --------------------------------------------------------------- |
| `mentor_turn_first_token_seconds` | Histogram | `sandbox` | From a message being accepted to the first text of Heph's reply |
| `mentor_turn_duration_seconds`    | Histogram | none      | A whole turn, from starting to run to its last chunk            |

`sandbox` is `warm` when the turn finds the developer's sandbox running.
It is `cold` when the turn must wait for a sandbox to start.
That can be its own startup, or one that Heph started moments before when it opened.
Web and Slack turns both count.
A turn that ends before any text records no first-token time.
The share of cold turns is the ratio of the two `_count` series:

```promql
sum(rate(mentor_turn_first_token_seconds_count{sandbox="cold"}[1h]))
  / sum(rate(mentor_turn_first_token_seconds_count[1h]))
```

`mentor_attach_duration_seconds` measures only one sandbox's startup, through the runner's first frame.
A high cold share means sandboxes are gone before developers write.
Possible causes are the idle TTL, a restart or deploy, or session caps.
A restart or deploy removes all Heph sandboxes.
See [Runtime Roles](./runtime-roles.mdx#interactive-mentor-turns) for sandbox preparation and the warm period.

## Privacy-job metrics

Account erasure, export generation, export expiry and LLM usage retention each report one terminal
outcome per run, published by the server role.

| Prometheus name               | Type    | Labels           | Meaning                                      |
| ----------------------------- | ------- | ---------------- | -------------------------------------------- |
| `privacy_job_completed_total` | Counter | `job`, `outcome` | Terminal privacy-job executions              |
| `privacy_job_affected_total`  | Counter | `job`            | Rows or subjects the run removed or produced |

`job` is one of `account_erasure`, `export_generation`, `export_retention`, or `llm_usage_retention`.
`outcome` is `success`, `incomplete`, or `failure`.
An empty backlog is a `success`.
No increase in the success counter therefore also warrants an alert.
`incomplete` means the run ended without error but exhausted its time budget while eligible work remained.

The LLM usage retention sweep deletes in batches for at most five minutes.
It reports `incomplete` when expired rows remain.
A deployment that reports this each day never finishes deletion.
Account, workspace, export, and source identifiers are not labels.
The [personal-data map](./dsms/personal-data-map.md) lists the erasure and retention paths these metrics cover.

For export generation, `success` and the affected count are published only after the export commits.
A failed attempt reports `failure` even if the database is unavailable and cannot save the failed
status. Consult the server log when an export remains queued or processing after a reported failure.

## Correlating a request

When tracing is enabled, HTTP responses carry an `X-Request-Id` header containing the request's W3C
trace ID. It is generated by tracing or extracted from valid incoming trace context, not derived
from user attributes. While a trace scope is active, JSON logs carry its IDs as `context.traceId` and
`context.spanId`. With tracing disabled, the correlation filter passes through without inventing an ID.
Access logs stay off at every layer.

A queued review records its submission correlation, but an execution attempt starts its own trace.
Join the request and subsequent lifecycle by `job.id`. Do not assume every log for a job shares the
request's trace ID. Sandbox proxy calls propagate the execution trace. The
[trace export contract](#exporting-opentelemetry-traces) describes the separate submission attribute.

No collector or log aggregator is necessary.
From a reference deployment:

1. Take the ID a user reports, or the `X-Request-Id` from a failed response.
2. Search the container logs:

   ```bash
   docker compose logs --no-color | grep '"traceId":"<the-id>"'
   ```

   That command finds records in the matching trace scope.
   To follow a queued job into later execution attempts:

3. Take its `job.id` from the queued event.
4. Search that identifier too.

Scheduler work can have execution traces without an original HTTP response.
A trace ID proves that correlation context was present, not that a collector received the trace.

## HTTP route metrics

`http.server.requests` uses route templates, not individual workspace slugs, message IDs, or query
strings. Its URI-tag budget is 256: enough for the supported route inventory and the framework's
bounded unmatched-request and management tags. A new URI beyond the budget is refused rather than
creating unbounded time series. A limit warning therefore means metrics are incomplete and needs
investigation, not a logging-level change.

Concrete IDs or URLs in `uri` tags indicate a tagging defect.

1. When the limit is reached, first inspect the actual `uri` tag values.
2. Fix a tagging defect before considering a larger budget.
3. Do not turn off the bound.

## Collecting logs

Hephaestus sends no logs and no error reports to any service.
The browser app reports nothing either.

### What the host keeps by default

The supported Compose stacks use Docker's `json-file` driver with a size limit for each container:

| Containers                                                                   | Limit                |
| ---------------------------------------------------------------------------- | -------------------- |
| `application-server`, `application-worker`, `webapp`, `postgres`, `volume-init` | 5 files of 50 MB |
| `webhook-server`, `nats-server`                                              | 3 files of 10 MB     |

Docker writes these files in its default blocking mode.
An application thread waits for the write, so no line is lost while the disk accepts writes.
When a container reaches its limit, Docker deletes its oldest file.
A line that no collector read before that deletion is lost.
Sandbox containers use the host's default Docker logging configuration, which Hephaestus does not change.

### Ship logs to Loki

This is optional.
[Grafana Alloy](https://grafana.com/docs/alloy/latest/) reads the host journal and sends the lines to a Loki that you operate.
Grafana then queries that Loki.
The repository ships an example only.
It does not start Alloy, and it names no destination.

1. Upgrade to a release with this log format first.
   Lines written by an earlier release are not redacted after the fact, and nothing in this setup collects them.
2. Add [`docker/observability/compose.journald.yaml`](https://github.com/hephaestus-build/Hephaestus/blob/main/docker/observability/compose.journald.yaml) after the single-host stack's compose files.
   It needs Compose 2.24.4 or later.
   It moves the three Java runtime roles, `application-server`, `application-worker` and `webhook-server`, to the `journald` driver and tags their entries `hephaestus-runtime`.
   The tag is new, so journal entries written before the overlay never match it.
   The webapp keeps its local `json-file` log: nginx error lines can name a client address and a request with its query.
   PostgreSQL keeps `json-file`, because its error lines can quote rejected row values.
   Sandbox containers, NATS and the proxy are not tagged.
3. The reference deployment renders each stack as its own Compose project.
   Give each of the three Java services the same `logging` block in that stack's override.
4. Run Alloy with [`docker/observability/config.alloy`](https://github.com/hephaestus-build/Hephaestus/blob/main/docker/observability/config.alloy).
   Set `LOKI_PUSH_URL` to your Loki push endpoint and `DEPLOYMENT_ENVIRONMENT` to the instance's name.
   The label reads `unset` when the variable is empty.
   Give Alloy read access to the journal through the `systemd-journal` group.
   That group can read the whole host journal, including `sshd` and `sudo` entries.
   The `matches` filter limits what Alloy ships, not what it can read, so treat the Alloy host account as privileged.
   Do not give it the Docker socket.
   The socket gives full control of the Docker daemon, also when you mount it read-only.
5. Set Loki's retention to the period in your record of processing.

The example reads only entries with the `hephaestus-runtime` tag.
It sets two index labels, `service_name` and `deployment_environment`.
Both come from a small fixed set.

The trace ID goes to [structured metadata](https://grafana.com/docs/loki/latest/get-started/labels/structured-metadata/), so `| trace_id="<id>"` finds a request without a label per request.
Workspace, job, user and repository identifiers stay in the line.
Read them with `| json`.
Do not make them labels: each value becomes its own stream ([Loki label best practices](https://grafana.com/docs/loki/latest/get-started/labels/bp-labels/)).

Each stage has a bound, and each bound can lose lines:

| Stage                       | Bound                                                    | When it is reached                     |
| --------------------------- | -------------------------------------------------------- | -------------------------------------- |
| Docker to journald          | 4 MiB buffer, non-blocking                               | Docker drops new lines. The app does not wait |
| journald                    | The host's `RateLimitBurst` and `SystemMaxUse`           | journald drops or deletes old entries  |
| Alloy start or long outage  | `max_age = "12h"`                                        | Older entries are not sent             |
| Alloy to Loki               | 10 retries, at most 5 minutes apart                      | Alloy drops the batch                  |

Hephaestus does not change `journald.conf`.
Check its limits on the host before you rely on the journal as a buffer.

## Exporting OpenTelemetry traces

Hephaestus uses Spring Boot's OpenTelemetry starter and the OTLP HTTP exporter. Export is disabled
by default. Configure these settings on the runtime
roles whose spans you want to collect:

| Variable                       | Default                           | Purpose                                                                        |
| ------------------------------ | --------------------------------- | ------------------------------------------------------------------------------ |
| `TRACING_OTLP_ENABLED`         | `false`                           | Enable the OTLP trace exporter.                                                |
| `TRACING_OTLP_ENDPOINT`        | `http://localhost:4318/v1/traces` | Full OTLP HTTP receiver URL, reachable from the application container.         |
| `TRACING_SAMPLING_PROBABILITY` | `0.0`                             | Fraction of new traces sampled. Use `1.0` for a dedicated evaluation instance. |

The supported Compose stack forwards these settings to server, worker and webhook containers.
Each span carries the running version as `service.version` and the deployment environment as `deployment.environment.name`.
For authenticated collectors, configure Spring Boot's
`management.opentelemetry.tracing.export.otlp.headers` through protected deployment configuration.
Do not put collector credentials in a URL. OTLP log and metric export stay disabled: enabling traces does not
start exporting application logs, private transcripts or a second metrics stream. Prometheus metrics
are available through the private listener described in [Scrape metrics](#scrape-metrics).

Each practice-review attempt starts a `practice_review.execute` span. Its trace ID can differ from
the job's submission correlation ID, which is carried as the `hephaestus.job.submission_trace_id`
attribute rather than as a parent span. Sandbox proxy requests propagate the
execution trace's sampling decision. A `gen_ai.chat`, `gen_ai.decision`, `gen_ai.embeddings` or
`gen_ai.rerank` span covers each authenticated model request, streamed or not. It records the model,
the HTTP outcome and the token usage that the provider reported, as `gen_ai.usage.input_tokens` and
`gen_ai.usage.output_tokens`. A reranking call that a provider billed in search units records
`hephaestus.usage.search_units` instead.

Framework HTTP spans describe the transport. Prompts, tool results, request bodies,
headers and tokens used for authentication are not span attributes.

For streaming requests, `hephaestus.stream.outcome` records transport completion separately from
the HTTP status. A client disconnect or stream failure marks the span as an error with a bounded
`error.type`, even if HTTP 200 headers were already sent. No replacement response body is sent
after the stream has been committed.

A trace ID is not proof of export. Sampling, exporter errors, collector retention and abrupt
process termination can all leave partial coverage. A trace describes when calls happened and how
they ended. It is not a record of what a review read or said.

Durable review records retain admitted results, their problems and citation checks, not raw inputs,
model requests or session transcripts. `AGENT_PAYLOAD_RETENTION` strips diagnostic job output.

The worker can separately retain bounded debug session transcripts. The
[retention decision](https://github.com/hephaestus-build/Hephaestus/blob/main/docs/decisions/0041-compose-1x-kubernetes-2.md#update--2026-10-09-debug-transcripts)
defines their ownership checks, metadata fallback, erasure and expiry.
