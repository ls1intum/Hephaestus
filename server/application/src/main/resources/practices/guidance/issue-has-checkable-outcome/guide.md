## How to do it

- Write each point of done so that someone who reads the issue can answer yes or no. For example, instead of “make search better”, write “a search for an exact title shows that issue first”.
- Pick the form that suits the work, such as a short checklist or a Given, When, Then block. The block gives the start state, the action, and the result you expect.
- For a bug, state the behavior that the fix must bring back.
- If a linked design document holds the finish line, check that it states what this work must do. A general guideline does not tell anyone when this issue is done.
- For an epic or another umbrella issue, define done as its child issues. Each child issue then carries its own finish line.

## When it does not apply

- The issue asks a question.
- The issue is a support request.
- The issue opens a discussion.
- The issue is a placeholder on a board or for a team meeting, with no problem and no requested change.

It still applies when the title names a task, such as “Add a dark-mode toggle”, and the body is empty.

## Common mistakes

- Adding a heading such as “Acceptance criteria” with vague points under it. The form does not matter. Instead, write each point so that someone can test it.
- Repeating the title in the body. Instead, add what will be true when the work is finished.
- Writing a goal that never ends, such as “improve performance”. Instead, name a result that someone can test.
- Agreeing on the finish line only in a call or a chat. Instead, write it in the issue or in a comment, so that someone can quote it later.

## Sources

- [INVEST in good stories, and SMART tasks](https://xp123.com/invest-in-good-stories-and-smart-tasks/), Bill Wake, 2003. A good story is testable. If nobody knows how to test it, the story may not be clear enough.
- [Given When Then](https://martinfowler.com/bliki/GivenWhenThen.html), Martin Fowler, 2013. A scenario states the starting state, the action, and the change that you expect.
- [Acceptance testing](https://agilealliance.org/glossary/acceptance/), Agile Alliance glossary. Acceptance tests describe behavior as examples or scenarios, and each one passes or fails.
