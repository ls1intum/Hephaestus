## How to do it

- Write about the code, never about the person who wrote it. Say what the code does, not what the author failed to do.
- When you have a concern, ask a real question or make a suggestion that the author can answer.
- When you ask for a change, give your reason. For example, instead of “Change this”, write “Could we use a map here? The list lookup scans the whole list for each item”.
- When you disagree, say what you prefer and why: “I’d prefer X because Y”.
- Before you post, remove sarcasm and any words that say the author should have known better.

## When it does not apply

- You wrote the pull or merge request. Your own comments on it do not count.
- A bot wrote the comment.
- The only comment is a bare approval, such as “LGTM” or “+1”.
- No reviewer has left a real comment yet, such as on a new pull or merge request.

It still applies when an account name looks automated but the account is not marked as a bot.

## Common mistakes

- Thinking that being direct is rude. A short, blunt comment about the code is fine, such as “This fails when the list is empty”. Strong technical disagreement is fine too. Keep the point clear, and keep it on the code.
- Checking only for single words such as “just” or “obviously”. Such a word is fine when it reads neutrally. Read the whole comment, and check where it points: at the code or at the author.
- Asking a question only to belittle, such as “Did you even run this?”. The author cannot answer it. Instead, say what you think is wrong and why.
- Letting frustration show when a change comes back again. Frustration, name-calling and impatience are common in uncivil reviews. Instead, restate the open concern and give your reason.

## Sources

- [How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html), Google Engineering Practices. Comment on the code and never on the developer, and often explain why you ask for a change.
- [Destructive criticism in software code review impacts inclusion](https://research.google/pubs/destructive-criticism-in-software-code-review-impacts-inclusion/), Gunawardena and others, 2022. The study surveyed 93 software practitioners. Women saw destructive criticism as less appropriate. They were also less motivated to keep working with the developer who gave it.
- [Characterizing incivility in open source code review discussions](https://doi.org/10.1145/3479497), Ferreira, Cheng and Adams, 2021. In Linux kernel reviews, the most frequent features of uncivil emails were frustration, name calling and impatience. The study also found civil ways to disagree.
