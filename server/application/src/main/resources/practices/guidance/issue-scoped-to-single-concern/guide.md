## How to do it

- Before you file the issue, name the one result that closes it. If closing it also needs a result with a different goal, that result is a second concern.
- Open one issue for each concern. For example, instead of one issue for dark mode and the login timeout, open two issues.
- Before you open a new issue, search the open issues for each ask. If an open issue already covers an ask, link to that issue in place of the ask.
- Keep all the steps of one result in its issue. A checklist that builds one feature belongs together, so a maintainer can assign, estimate and close it as one thing.
- For an epic, a large issue for one feature area, keep the related parts of that area together. Create, rename and delete for one item are one concern at that level.

## When it does not apply

- The issue asks a question and asks for no work.
- The issue is a support request.
- The issue opens a discussion and names nothing to build or fix yet.
- The body is empty, or the issue has only a title.
- The body is the issue template, with nothing changed.

## Common mistakes

- Splitting an issue because its title has “and” or its checklist is long. Neither one makes it a bundle. Instead, look for asks with different goals that could each land and close on their own.
- Adding an unrelated ask to an open issue to save time. Different people often handle different asks, and an ask that hides in another issue can stay undone. Instead, open a new issue for it.
- Splitting the asks into issues that do not point to each other. Instead, link each new issue to the others, so the context stays easy to find.

## Sources

- [Bug Writing Guidelines](https://bugzilla.mozilla.org/page.cgi?id=bug-writing.html), Mozilla. Open a new report for each issue, so the fix workflow can finish for each one.
- [How to pre-screen Browser-General bugs](https://www-archive.mozilla.org/quality/browser/prescreening), Mozilla, 2004, archived page. A report that lists several unrelated problems goes to different engineers, and some of its problems may never get fixed.
- [INVEST in good stories, and SMART tasks](https://xp123.com/invest-in-good-stories-and-smart-tasks/), Bill Wake, 2003. Stories are easiest to work with when they do not overlap and can be built in any order. A good story can be estimated.
