## How to do it

- When an existing test fails after your change, fix the cause. Do not weaken the test to make it pass.
- When you update a test for new behavior, keep its check as strong as before.
- When you move, rename or split a test, carry every assertion with it.
- If a test must go, say in the description or a commit message how your change made it obsolete. For example, instead of deleting a rounding test with no reason, write that your change removes rounding.
- If your change means a test should no longer run, write why in the skip itself. Tie the reason to your change, such as the text of `@Disabled("…")` in JUnit or `reason=` in pytest.

## When it does not apply

- Your change edits no existing test or assertion. For example, it adds a feature and changes no tests.
- Your change is empty.
- The only tests that you changed are generated by a tool or copied in from another project.
- Your change only adds new tests.

It still applies when you change an existing test and keep it just as strong. It also applies when a few hand-written test lines sit among many generated files.

## Common mistakes

- Treating every edit to a test as weakening the suite. A move, a rename or a split is fine. So is deleting a test together with the code it tests. Instead, ask one question: can the test still fail on the bug it guarded?
- Hollowing out a test instead of removing it. An always-true assertion or commented-out test code leaves a test that passes but checks nothing. Instead, restore the check, or remove the test and say why.
- Giving a reason that explains nothing. “Fix later” does not say why a test that still matters can go. Instead, fix the cause, or explain how your change made the test obsolete.
- Skipping a test and moving on. Many skipped tests stay skipped for years. Instead, fix the cause in this change when you can.

## Sources

- [Unit testing](https://abseil.io/resources/swe-book/html/ch12.html), Erik Kuefler, Software Engineering at Google, 2020. A refactoring, a new feature or a bug fix should not need changes to existing tests. Only a change in behavior should.
- [How disabled tests manifest in test maintainability challenges?](https://doi.org/10.1145/3468264.3468609), Kim, Yang, Yang and Chen, 2021. In 15 open-source Java projects, about 41% of disabled tests never came back, and most stayed disabled for years.
- [Disabling tests](https://docs.junit.org/current/writing-tests/disabling-tests.html), JUnit User Guide, the JUnit team. A reason is optional, but the JUnit team recommends a short reason for each disabled test.
