## How to do it

- Before you close an issue as done, read its checklist and its sub-issues.
- Tick each checklist item that the work finished.
- Close each sub-issue that is finished.
- If an item is still open, name it in a closing comment that you post when you close. Say why it is dropped or deferred. For example, instead of closing with “Done”, write “Done except PDF export. We deferred it until the export library is ready.”
- If you drop the whole issue, close it as not planned instead of as done.

## When it does not apply

- You close the issue as not planned.
- You close it as wontfix, because you will not fix it.
- You close it as a duplicate of another issue.
- You close it as superseded, because other work replaced it.
- You close it as deferred, to come back to it later.

## Common mistakes

- Closing finished work with its boxes still empty. The work may be done, but the issue still says that it is open. Instead, tick each finished item before you close.
- Closing with “Done” or with no comment while an item is still open. The open item then looks finished. Instead, name the item and say why it is dropped or deferred.
- Adding the note or ticking the boxes days after the close. Until then, the team reads the issue as done. Instead, do it before you close, or in the same step.
- Leaving sub-issues open under a parent that you close as done. Instead, finish them first. Or name them in the closing comment.

## Sources

- [Closing an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/closing-an-issue), GitHub Docs. You can choose a close reason to show that work is finished or not planned.
- [Manage issues](https://docs.gitlab.com/user/project/issues/managing_issues/), GitLab Docs. The `/close` quick action can close an issue from a comment.
- [The Scrum Guide](https://scrumguides.org/scrum-guide.html), Ken Schwaber and Jeff Sutherland, 2020. In Scrum, work that fails the team’s agreed quality checks returns to their list of future work.
